## 1. 位置づけ

`@othello/cpu` の `evaluate.ts` は、対局が続いている局面を**手番側の視点で 1 つの整数**に要約する。要件定義 §9.1 が「つよい」に課す「**位置評価・着手可能数・確定石**を含む評価関数」の実体にあたる。

| 関係       | 相手                                                                         |
| ---------- | ---------------------------------------------------------------------------- |
| 呼び出し元 | `search.ts`（葉局面で呼ぶ）／`think.ts`（重みを束縛して `Evaluator` を作る） |
| 依存       | `@othello/core` のみ                                                         |
| 対応要件   | §9.1（強度ごとの評価内容）／§17（テスト方針）／O-06（重みの調整）            |

強度による評価の差は**評価関数の実装を分けることでは表さない**。評価関数は 1 本とし、成分ごとの**重み**を `level.ts` の強度パラメータ表で切り替える（`../モジュール定義.md` §4 の設計判断「評価関数の強度差」）。

## 2. 公開 API

```ts
/** 評価成分ごとの重み。すべて整数（§3） */
export type EvalWeights = {
    /** 石差。終盤以外では小さく取る（§4.1） */
    readonly stoneDiff: number;
    /** 位置評価。角を取り、X 打ち・C 打ちを避ける方向に効く（§4.2） */
    readonly position: number;
    /** 着手可能数。相手の選択肢を狭める方向に効く（§4.3） */
    readonly mobility: number;
    /** 確定石。ひっくり返されない石を増やす方向に効く（§4.4） */
    readonly stable: number;
};

/**
 * 局面を player の視点で評価する。
 * 対局が続いている局面にのみ用いる（終局の評価は search.ts の terminalScore が担う）。
 */
export function evaluate(board: Board, player: Player, weights: EvalWeights): number;

/** 位置評価表。search.ts の着手順序でも共有する（search.md §5） */
export const POSITION_WEIGHTS: readonly (readonly number[])[];
```

### 2.1 `@othello/core` から使う API

| 用途         | API                                   |
| ------------ | ------------------------------------- |
| 石数の集計   | `countCells(board)`                   |
| 合法手の列挙 | `listLegalMoves(board, player)`       |
| 相手色       | `opponent(player)`                    |
| 盤の一辺     | `BOARD_SIZE`                          |
| 型           | `Board` / `Player` / `Cell` / `Coord` |

`countStones(board, player)` は内部で `countCells` を呼ぶため、黒白の両方が要る場面では `countCells` を 1 回だけ呼ぶ。評価関数は探索の葉で毎回呼ばれるため、盤面の全走査の回数を抑える。

## 3. 評価値の規約

| 規約     | 内容                                                                                                     |
| -------- | -------------------------------------------------------------------------------------------------------- |
| 視点     | 常に `player` 視点。`player` に有利なら正、不利なら負、互角なら 0                                        |
| **整数** | 返り値は必ず整数。`search.md` §4.3 の「根で窓を `best - 1` にする」設計がこれに依存する                  |
| 対称性   | `evaluate(board, "black", w) === -evaluate(board, "white", w)` が常に成り立つ                            |
| 適用範囲 | 対局が続いている局面のみ。終局局面は `search.ts` の `terminalScore` が扱う（`search.md` §3.2）           |
| 値域     | 各成分の上限と重みから見積もる。`search.ts` の `WIN_SCORE = 1_000_000` より十分小さいこと（§5.2 で確認） |

すべての成分は「`player` の値 − 相手の値」の差分として定義する。これにより対称性が構造的に保たれる。

```ts
export function evaluate(board: Board, player: Player, weights: EvalWeights): number {
    const foe = opponent(player);
    const count = countCells(board);

    const stoneDiff = count[player] - count[foe];
    const position = positionScore(board, player) - positionScore(board, foe);
    const mobility = listLegalMoves(board, player).length - listLegalMoves(board, foe).length;
    const stable = countStableDiscs(board, player) - countStableDiscs(board, foe);

    return (
        weights.stoneDiff * stoneDiff +
        weights.position * position +
        weights.mobility * mobility +
        weights.stable * stable
    );
}
```

重みが 0 の成分も計算してから 0 を掛ける形になるが、M4 ではこの単純さを採る。O-06 の実測で葉の評価が律速だと分かった場合は、重み 0 の成分の計算を飛ばす最適化を検討する。

## 4. 成分ごとの仕様

### 4.1 石差（`stoneDiff`）

```
stoneDiff = （player の石数） − （相手の石数）
```

`countCells(board)` の結果から直接得る。

**注意**: 序盤・中盤の石差は強さと**逆相関**することが知られている（石が少ない方が着手可能数を保ちやすい）。したがって「ふつう」「つよい」では石差の重みを小さく取り、勝敗に直結する終盤は `endgame.ts` の完全読みに委ねる（§6）。石差を主役にするのは「やさしい」の貪欲法（`greedy.ts`）であり、そちらは評価関数を使わない。

局面の進行度に応じて重みを変える設計（フェーズ依存の重み）は、`../モジュール定義.md` §3.1 の `LevelConfig` が重みを 1 組しか持たないため **M4 では採らない**。

### 4.2 位置評価（`position`）

各マスに静的な重みを与え、自石のマスの重みの合計から相手石のマスの重みの合計を引く。

```ts
function positionScore(board: Board, player: Player): number {
    let total = 0;
    for (let row = 0; row < BOARD_SIZE; row++) {
        for (let col = 0; col < BOARD_SIZE; col++) {
            if (board[row]![col] === player) total += POSITION_WEIGHTS[row]![col]!;
        }
    }
    return total;
}
```

**位置評価表の初期案**（`board[row][col]` に対応。`row = 0` が行 1、`col = 0` が列 a。左上が a1）

| row\col |   a |   b |   c |   d |   e |   f |   g |   h |
| ------- | --: | --: | --: | --: | --: | --: | --: | --: |
| **1**   | 100 | -20 |  10 |   5 |   5 |  10 | -20 | 100 |
| **2**   | -20 | -50 |  -2 |  -2 |  -2 |  -2 | -50 | -20 |
| **3**   |  10 |  -2 |   1 |   1 |   1 |   1 |  -2 |  10 |
| **4**   |   5 |  -2 |   1 |   0 |   0 |   1 |  -2 |   5 |
| **5**   |   5 |  -2 |   1 |   0 |   0 |   1 |  -2 |   5 |
| **6**   |  10 |  -2 |   1 |   1 |   1 |   1 |  -2 |  10 |
| **7**   | -20 | -50 |  -2 |  -2 |  -2 |  -2 | -50 | -20 |
| **8**   | 100 | -20 |  10 |   5 |   5 |  10 | -20 | 100 |

| マス                                     | 重み | 理由                                                                   |
| ---------------------------------------- | ---: | ---------------------------------------------------------------------- |
| 角（a1・h1・a8・h8）                     |  100 | 絶対にひっくり返されない。要件定義 §9.1 の「やさしい」も角を最優先する |
| X 打ち（b2・g2・b7・g7）                 |  -50 | 角に斜めで接する。相手に角を与えやすい最悪のマス                       |
| C 打ち（a2・b1・g1・h2・a7・b8・g8・h7） |  -20 | 角に辺で接する。角を与えるきっかけになりやすい                         |
| 辺の中央寄り（c1・f1 等）                |   10 | 辺は返されにくく、確定石に育ちやすい                                   |
| 中央 4 マス（d4・e4・d5・e5）            |    0 | 初期配置で埋まっており、評価に差が出ない                               |

表は上下・左右・対角のいずれにも対称であり、`evaluate` の対称性（§3）を壊さない。

**この簡易表の限界**: 角が既に取られている場合、その角に隣接する C 打ち・X 打ちの危険度は実際には消える（角を取った側にとっては安全なマスになる）。静的な表はこれを表現できない。M4 ではこの誤差を許容し、角を取ったあとの局面は探索の深さで補う。

**共有**: この表は `search.ts` の着手順序（`search.md` §5）でも使う。重複定義を避けるため `evaluate.ts` が公開し、`search.ts` が import する。

### 4.3 着手可能数（`mobility`）

```
mobility = listLegalMoves(board, player).length − listLegalMoves(board, 相手).length
```

自分の選択肢が多く、相手の選択肢が少ないほど良い。相手の合法手を 0 にできればパスを強制でき、連続手番につながる。オセロで最も効く指標の 1 つであり、「つよい」では重みを大きく取る（§5）。

`listLegalMoves` は盤面を 2 周（64 マス × 8 方向の走査）するため、評価成分の中で最も重い。重みを 0 にしても現状は計算される点に注意（§3 末尾）。

### 4.4 確定石（`stable`）

**確定石**とは、以後どの手順でも二度とひっくり返されない石をいう。要件定義 §9.1 が「つよい」にのみ課している指標である。

**採用する簡易判定**: 角から辺に沿って自石が途切れずに続く範囲を確定石とみなす。

```ts
/** 4 つの角と、その角から辺に沿って伸びる 2 方向 */
const CORNER_RAYS = [
    {
        corner: { row: 0, col: 0 },
        rays: [
            { row: 0, col: 1 },
            { row: 1, col: 0 },
        ],
    },
    {
        corner: { row: 0, col: 7 },
        rays: [
            { row: 0, col: -1 },
            { row: 1, col: 0 },
        ],
    },
    {
        corner: { row: 7, col: 0 },
        rays: [
            { row: 0, col: 1 },
            { row: -1, col: 0 },
        ],
    },
    {
        corner: { row: 7, col: 7 },
        rays: [
            { row: 0, col: -1 },
            { row: -1, col: 0 },
        ],
    },
] as const;

function countStableDiscs(board: Board, player: Player): number {
    // 辺が両端の角から埋まっている場合に二重計上しないよう、座標を集合で持つ
    const stable = new Set<string>();

    for (const { corner, rays } of CORNER_RAYS) {
        if (board[corner.row]![corner.col] !== player) continue;
        stable.add(`${corner.row},${corner.col}`);

        for (const ray of rays) {
            let row = corner.row + ray.row;
            let col = corner.col + ray.col;
            while (
                row >= 0 &&
                row < BOARD_SIZE &&
                col >= 0 &&
                col < BOARD_SIZE &&
                board[row]![col] === player
            ) {
                stable.add(`${row},${col}`);
                row += ray.row;
                col += ray.col;
            }
        }
    }

    return stable.size;
}
```

**この近似の限界**

| 数えられないもの                                       | 影響     |
| ------------------------------------------------------ | -------- |
| 盤の内部にある確定石（周囲が埋まって動かなくなった石） | 過小評価 |
| 辺が完全に埋まったときの、角を含まない辺の石           | 過小評価 |
| 確定石に囲まれて確定した石                             | 過小評価 |

いずれも**過小評価であって過大評価ではない**ことが重要である。確定していない石を確定と誤認すれば「安全だと信じて角を手放す」という致命的な判断を生むが、その方向の誤りは起きない。

より正確な判定（各石について 4 つの軸すべてで「盤端まで埋まっている」または「確定石に接している」ことを反復的に求める方法）は計算量が大きく、M4 では見送る。O-06 の実測後、「つよい」に余力があれば再検討する。

## 5. 強度ごとの重みの初期案

**以下の値はすべて暫定であり、O-06（要件定義 §20、決定期限 M4）の実測とテスト対局を経て `level.ts` で調整する。** 本節の値は「調整の出発点」であって仕様ではない。

### 5.1 初期案

| 強度               | `stoneDiff` | `position` | `mobility` | `stable` | 備考                                       |
| ------------------ | ----------: | ---------: | ---------: | -------: | ------------------------------------------ |
| `easy`（やさしい） |           — |          — |          — |        — | 評価関数を使わない（`greedy.ts` で貪欲法） |
| `normal`（ふつう） |           1 |          5 |          2 |        0 | 確定石を使わない                           |
| `strong`（つよい） |           1 |          5 |         10 |       25 | 着手可能数と確定石を重く見る               |

**`normal` が確定石を使わない理由**: 要件定義 §9.1 は確定石を「つよい」の評価関数にのみ挙げている。強度の性格を分けるうえでも、最も重い成分を「つよい」専用にするのは探索速度の面で都合がよい。「ふつう」の重み `stable: 0` はこの意図を表す（計算はされるが評価に寄与しない。§3 末尾の最適化余地）。

**`strong` の重み配分の意図**: 中盤は着手可能数で相手を締め上げ、確定石で優位を固定する。石差は勝敗の最終指標ではあるが序盤・中盤では逆相関するため、重みを 1 に留めて他の成分に判断を委ねる。

### 5.2 値域の確認

`search.ts` の `WIN_SCORE = 1_000_000`（`search.md` §3.4）を、評価値が超えないことを確認する。`strong` の重みでの粗い上限は次のとおり。

| 成分        | 差分の上限（絶対値） | 重み |   寄与の上限 |
| ----------- | -------------------: | ---: | -----------: |
| `stoneDiff` |                   64 |    1 |           64 |
| `position`  |             約 1,000 |    5 |        5,000 |
| `mobility`  |                約 30 |   10 |          300 |
| `stable`    |                   28 |   25 |          700 |
| **合計**    |                      |      | **約 6,100** |

`WIN_SCORE` の 1/100 以下に収まっており、終局の評価が常に優先される（`search.md` §3.4 の要請を満たす）。重みを大幅に引き上げる調整を行う場合は、この見積りを再計算すること。

## 6. 終盤（完全読み）での扱い

「つよい」が終盤で完全読みに切り替わったときは、**石差のみ**を用いる（`../モジュール定義.md` §3.1 の `endgame.ts` の責務）。

終局まで読み切る以上、位置評価・着手可能数・確定石といった「勝ちやすさの近似指標」は不要であり、勝敗を直接決める石数だけが意味を持つためである。要件定義 §6「終局時の石数が多い方の勝ち」と一致する。

実現方法は評価関数の差し替えではなく、**重みの差し替え**とする。

```ts
/** 完全読みで用いる重み。石差のみ */
export const ENDGAME_WEIGHTS: EvalWeights = {
    stoneDiff: 1,
    position: 0,
    mobility: 0,
    stable: 0,
};
```

ただし完全読みでは探索が必ず終局に到達するため、実際の評価はほぼすべて `search.ts` の `terminalScore`（石差 + `WIN_SCORE`）が返す。`ENDGAME_WEIGHTS` が使われるのは、時間切れで読み切れず葉に達した場合に限られる（`deepening.md` を参照）。その場合も石差で判断するのが自然である。

## 7. `core` の公開 API との関係

`countStableDiscs`（§4.4）と `positionScore`（§4.2）は盤面を方向ベクトルで走査するが、**`@othello/core` の `DIRECTIONS` / `step` / `isOnBoard` と `Direction` 型は `core/index.ts` が再エクスポートしていない**（`core/index.ts` の規約: 「パッケージ外から参照できるのはこのファイルが再エクスポートした要素に限る」）。

**判断: `evaluate.ts` が必要な方向ベクトルを自前で持つ。** `core` のバレルを広げない。

| 選択肢                                   | 採否     | 理由                                                                                                           |
| ---------------------------------------- | -------- | -------------------------------------------------------------------------------------------------------------- |
| `cpu` 側で方向ベクトルを定義する         | **採用** | `core` の公開 API を広げずに済む。確定石判定で必要なのは角から伸びる 8 本の走査だけで、汎用の 8 方向は要らない |
| `core/index.ts` に `DIRECTIONS` 等を追加 | 不採用   | `core` の公開面を広げると、合法手判定の内部実装が外部から使える状態になる。バレル規約の意図に反する            |

`CORNER_RAYS`（§4.4）はこの判断に基づく `evaluate.ts` 内のローカル定数である。`core` の `Direction` 型も使えないため、`{ row, col }` のオブジェクトリテラルで表す。

## 8. テスト観点

要件定義 §17 の「CPU 思考: 既知の局面で妥当な手を選ぶこと」に対応する。本モジュールは決定的な純関数なので、すべて同期のユニットテストで検証できる。

### 8.1 成分を 1 つずつ切り分ける

**重みを 1 成分だけ 1 にし、他を 0 にする**ことで、成分単体の妥当性を独立に検証できる。これが「評価関数を 1 本にして重みで切り替える」設計（`../モジュール定義.md` §4）を採った主な理由である。

| #   | 対象        | 重み                                                    | 検証内容                                                                                                   |
| --- | ----------- | ------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------- |
| 1   | `stoneDiff` | `{ stoneDiff: 1, position: 0, mobility: 0, stable: 0 }` | 黒が多い局面で黒視点が正、白視点が負。石数が等しければ 0                                                   |
| 2   | `position`  | `{ position: 1, 他 0 }`                                 | 角のみに自石がある局面で +100。X 打ちのみなら -50。初期盤面（中央 4 マス）は 0                             |
| 3   | `mobility`  | `{ mobility: 1, 他 0 }`                                 | 自分だけが打てる局面で正。相手だけが打てる局面で負                                                         |
| 4   | `stable`    | `{ stable: 1, 他 0 }`                                   | 角 1 つだけ自石なら +1。角から辺に自石が 3 つ続けば +3。辺が両端の角から埋まった場合に二重計上されないこと |

### 8.2 全体の性質

| #   | 観点         | 内容                                                                                                     |
| --- | ------------ | -------------------------------------------------------------------------------------------------------- |
| 5   | 対称性       | 任意の局面・任意の重みで `evaluate(b, "black", w) === -evaluate(b, "white", w)`                          |
| 6   | **整数性**   | 初期案の全重みで、複数の既知局面に対し `Number.isInteger(evaluate(...))` が真（`search.md` §4.3 の前提） |
| 7   | 値域         | §5.2 の見積りどおり、初期案の重みで `WIN_SCORE` を超えないこと                                           |
| 8   | 符号の妥当性 | 「角を 4 つ取った側」「相手をパスに追い込んだ側」が `strong` の重みで正の評価を得ること                  |
| 9   | 決定性       | 同じ入力を複数回呼んで同じ値が返ること（`Math.random()` / `Date.now()` を使っていないことの確認）        |

### 8.3 `POSITION_WEIGHTS` 自体のテスト

| #   | 観点   | 内容                                                                      |
| --- | ------ | ------------------------------------------------------------------------- |
| 10  | 形     | 8 行 × 8 列であること                                                     |
| 11  | 対称性 | 上下反転・左右反転・転置のいずれでも同じ表になること（§3 の対称性の前提） |
| 12  | 整数性 | すべての要素が整数であること                                              |

## 9. O-06 との関係

本モジュールが O-06（要件定義 §20「CPU 各強度の探索深さと思考時間上限」。`../モジュール定義.md` §6 により「完全読み閾値」「最低思考時間」も対象に追加）へ与える影響は 2 つある。

1. **評価の重さが到達深さを決める**。着手可能数（§4.3）と確定石（§4.4）は葉ごとに盤面を走査するため、`strong` の評価は `normal` より 1 手あたりのコストが高い。同じ時間上限でも到達深さが浅くなりうる
2. **重みそのものが調整対象**。§5 の初期案は暫定値であり、実測と対局結果に応じて `level.ts` で変更する

`bench.ts` では、評価成分の有効・無効を切り替えたときの 1 秒あたりの探索ノード数も併せて出力し、「確定石を入れる価値が深さの低下に見合うか」を判断できるようにする（要件定義 §17 実機）。
