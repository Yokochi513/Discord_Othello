## 1. 位置づけと関連要件

`deepening.ts` は **反復深化と思考時間管理**を担う。固定深さの探索そのものは `search.ts` が行い、本モジュールは「どの深さまで読むか」「いつ打ち切るか」だけを決める。

| 要件          | 内容                                                                                        | 本モジュールでの扱い                                               |
| ------------- | ------------------------------------------------------------------------------------------- | ------------------------------------------------------------------ |
| 要件定義 §9.2 | 思考時間に上限を設ける。上限に達した時点で、その時点の最善手を返す（反復深化）              | 本モジュールの存在理由そのもの                                     |
| 要件定義 E-12 | CPU の思考が上限時間を超えた → その時点の最善手を打つ                                       | §4 で担保方法を定める                                              |
| 要件定義 R-02 | ラズパイの性能が「つよい」の探索に耐えない → 反復深化＋上限で深さが自動的に決まる設計にする | 到達深さを固定せず、時間が許す範囲で深くする（§3）                 |
| 要件定義 §17  | CPU 思考は「妥当な手を選ぶこと」と「思考時間上限を守ること」を**別々に**検証する            | 前者は `search.ts`、後者は本モジュールの責務（§7・§8）             |
| 要件定義 O-06 | 探索深さと思考時間上限は実測で決定する（期限 M4）                                           | 値は持たず `level.ts` から受け取る。本モジュールは挙動のみを定める |

**本モジュールが持たないもの**: 評価関数（`evaluate.ts`）、探索木の走査（`search.ts`）、強度ごとの具体値（`level.ts`）、worker やタイマーなどの実行基盤（`server/cpuDriver.ts`）。

## 2. 公開 API

### 2.1 シグネチャ

```ts
export function deepen(
    board: Board,
    player: Player,
    config: SearchConfig,
    deps: ThinkDeps,
): DeepenResult;
```

`Board` / `Player` は `@othello/core` の型。`ThinkDeps` は `{ now: () => number; random: () => number }`（`../モジュール定義.md` §3.1）。本モジュールは `deps.now` のみを使い、`deps.random` は使わない（乱択は `think.ts` の責務）。

### 2.2 型定義

```ts
/** 反復深化に必要な探索設定。LevelConfig の algorithm: "search" 側から取り出した部分 */
export type SearchConfig = {
    /** 反復深化の上限。ここへ到達したら打ち切る */
    readonly maxDepth: number;
    /** 思考時間の上限（ミリ秒）。要件定義 §9.2 / O-06 */
    readonly timeLimitMs: number;
    /** 評価関数の重み。完全読みでは石差のみを有効にする（endgame.md） */
    readonly weights: EvalWeights;
};

/** 反復深化の結果 */
export type DeepenResult = {
    /** 最善手。同じ評価値で並んだ手が複数ある場合はすべて含む（1 つ以上を必ず返す） */
    readonly moves: readonly Coord[];
    /** 実際に完了した反復の深さ。1 度も完了しなかった場合は 0 */
    readonly depth: number;
    /** 全変化が終局に到達し、それ以上深くしても結果が変わらない状態か */
    readonly exhausted: boolean;
    /** 思考に要した時間（ミリ秒）。ログと O-06 の実測に用いる */
    readonly elapsedMs: number;
};
```

`moves` を**配列で返す**のは、同点の最善手からの乱択を `think.ts` が行うため（`../モジュール定義.md` §4 の「乱択」）。本モジュールは選ばず、候補をそのまま渡す。

### 2.3 事前条件・事後条件

| 区分     | 内容                                                                                                        |
| -------- | ----------------------------------------------------------------------------------------------------------- |
| 事前条件 | `player` に合法手が 1 つ以上あること（`listLegalMoves(board, player).length > 0`）。保証するのは `think.ts` |
| 事前条件 | `config.maxDepth >= 1` かつ `config.timeLimitMs > 0`                                                        |
| 事後条件 | `moves` は必ず 1 つ以上の合法手を含む（§4.2 のフォールバックにより保証する）                                |
| 事後条件 | 元の `board` を破壊しない（`core` の盤面は凍結済み。探索は新しい盤面を生成する）                            |

事前条件に違反した場合は例外を投げる。合法手が無い局面は**パスであって思考の対象ではない**ため、呼び出し側の誤りとして扱う。

## 3. 反復深化のアルゴリズム

### 3.1 擬似コード

```
function deepen(board, player, config, deps):
    started = deps.now()
    deadline = started + config.timeLimitMs

    legal = listLegalMoves(board, player)
    if legal.length === 0:
        throw （事前条件違反）

    // 深さ 0 のフォールバック。1 度も反復が完了しなくても必ず手を返せるようにする（§4.2）
    best = { moves: legal, depth: 0, exhausted: false }
    lastIterationMs = 0

    for depth = 1 to config.maxDepth:
        // 打ち切り条件 (1): 上限時間に達している
        if deps.now() >= deadline: break

        // 打ち切り条件 (2): 次の反復が上限内に終わる見込みがない（§3.3）
        if not shouldStartNextIteration(deps.now(), deadline, lastIterationMs): break

        iterationStarted = deps.now()
        result = searchBestMoves(board, player, depth, evaluateWith(config.weights))
        lastIterationMs = deps.now() - iterationStarted

        // 反復は必ず完走する（中断しない）ため、結果は常に採用してよい（§5）
        best = { moves: result.moves, depth, exhausted: result.exhausted }

        // 打ち切り条件 (3): 全変化が終局に到達した。これ以上深くしても結果は変わらない
        if result.exhausted: break

    return { ...best, elapsedMs: deps.now() - started }
```

`searchBestMoves` の戻り値に `exhausted`（探索した全変化が終局に到達したか）を含める点は `search.md` 側の契約とする。

### 3.2 打ち切り条件

| #   | 条件                         | 判定箇所             | 意味                                                       |
| --- | ---------------------------- | -------------------- | ---------------------------------------------------------- |
| 1   | 上限時間に達した             | 反復の開始前         | E-12 の基本ケース                                          |
| 2   | 次の反復が間に合わない見込み | 反復の開始前（§3.3） | 上限の超過を抑える予測判断                                 |
| 3   | `maxDepth` に到達した        | ループ条件           | `level.ts` が定めた強度の上限（O-06）                      |
| 4   | 全変化が終局に到達した       | 反復の完了後         | それ以上深くしても結果が変わらない。完全読みの自然な終了点 |

### 3.3 次の反復を始めるかの予測判断

`search.ts` は**中断できない**（§4.3）。したがって深さ `d+1` の反復を始めるかどうかは、始める前に判断しなければならない。

```
function shouldStartNextIteration(now, deadline, lastIterationMs):
    if lastIterationMs === 0: return true          // 初回は必ず 1 度は試す
    estimated = lastIterationMs * BRANCHING_ESTIMATE
    return now + estimated <= deadline
```

- `BRANCHING_ESTIMATE` は「深さが 1 増えたときに所要時間が何倍になるか」の見積り。α-β 枝刈りが効いた状態でおよそ **3〜6 倍**を見込む
- 具体値は **O-06 の実測対象**とし、`level.ts` ではなく本モジュールの定数として持つ（強度によらず探索の性質で決まるため）
- 見積りが小さすぎれば上限を超過し、大きすぎれば到達深さが不必要に浅くなる。`bench.ts` の実測で調整する

**初回（深さ 1）は予測せず必ず実行する。** 深さ 1 は合法手を 1 手ずつ評価するだけで、オセロでは最大 30 手程度・マイクロ秒オーダーで終わるため、上限がどれだけ短くても実行できる。

## 4. 思考時間上限の担保（E-12）

### 4.1 二段構えの上限

`search.ts` が中断できない以上、本モジュール単独では上限を**厳密には**守れない。深さ `d+1` の反復に入った後、それが予測より長引けば上限を超える。そのため上限は 2 段構えで担保する。

| 段     | 担保する場所                   | 方式                                                       | 守れる精度                       |
| ------ | ------------------------------ | ---------------------------------------------------------- | -------------------------------- |
| ソフト | `deepening.ts`（本モジュール） | 反復の境界で時刻を見て、次を始めない（§3.2・§3.3）         | 反復 1 回分の超過がありうる      |
| ハード | `server/cpuDriver.ts`          | 上限＋猶予を過ぎたらウォッチドッグが worker を `terminate` | 確実。ただし思考結果は捨てられる |

ハード側が発動した場合、`cpuDriver.ts` は `greedy.ts` の手にフォールバックして対局を続行する（`../モジュール定義.md` §4「思考失敗時」）。つまり **E-12 の「必ず何らかの手を打つ」は二段構えで満たされる**が、ハード側に落ちると手の質が下がるため、ソフト側の予測精度（§3.3）が実質的な品質を決める。

猶予の具体値は O-06 の実測後に決める。目安として `timeLimitMs` の 1.5〜2 倍を想定する。

### 4.2 最悪ケースのフォールバック

深さ 1 の反復すら完了しなかった場合（上限が極端に短い、または擬似時計を用いたテスト）、`best` は初期値のままとなり、`moves` には `listLegalMoves` の結果がそのまま入る。

- `listLegalMoves` の走査順は a1 → h8 で固定されている（`core/moves.ts`）ため、結果は決定的
- `depth: 0` が「探索していない手」であることを呼び出し側とログに伝える
- この場合でも `moves` は空にならないため、**`deepen` は必ず合法手を返す**という事後条件（§2.3）が保たれる

### 4.3 検討して採らなかった案：`search` への deadline 注入

`searchBestMoves` に締切を渡し、探索の途中で打ち切れるようにすれば上限を厳密に守れる。しかし採らない。

| 論点         | 内容                                                                                                                                             |
| ------------ | ------------------------------------------------------------------------------------------------------------------------------------------------ |
| 決定性       | `search.ts` が時間に依存すると、同じ局面・同じ深さでも開発機とラズパイで結果が変わる。「この局面で深さ 4 なら `e6`」というテストが成立しなくなる |
| 要件との対応 | 要件定義 §17 が「妥当な手を選ぶこと」と「上限を守ること」を別項目として挙げている構造に、モジュール分割を合わせている                            |
| 契約         | `../モジュール定義.md` §3.1 が `searchBestMoves(board, player, depth, evaluate)` の 4 引数を契約として定めている                                 |

代償として反復 1 回分の超過を許容し、§4.1 のハード側で塞ぐ。**O-06 の実測で超過が許容できないと判明した場合**は、テストで締切を省略できる省略可能引数として再検討する余地を残す。

## 5. 最善手の引き継ぎ

**方針: 不完全な反復の結果は採用しない。**

本設計では `search.ts` が中断されないため、反復は「完走する」か「そもそも始まらない」かの 2 通りしかなく、**不完全な結果は原理的に生じない**。これは §4.3 で決定性を優先した分割の副次的な利点である。

将来 §4.3 を見直して中断可能にする場合も、途中結果は採用せず**直前に完了した深さの結果を返す**方針とする。理由は次のとおり。

- α-β 探索は着手順序に依存して枝刈りする。深さ `d` の探索を途中で止めた時点の暫定最善手は、まだ評価していない手を含まないため、深さ `d-1` の完了結果より悪いことがありうる
- 深さ `d-1` の結果は、その深さにおける全候補を評価し終えた一貫した結果である
- 「浅くても一貫した手」のほうが「深いが偏った手」より安定して強い

## 6. 完全読みもこのモジュールを通す理由

終盤の完全読み（`endgame.md`）は、評価関数を使わず残り空きマス数を深さとして終局まで読む探索である。これを `endgame.ts` が独立して実行する設計も考えられるが、**必ず `deepen` を経由させる**（`../モジュール定義.md` §4「完全読みの経路」）。

1. **E-12 の担保を 1 か所に保つ。** 別経路にすると時間上限の管理が 2 か所に分かれ、ラズパイで残り 12 マスの完全読みが上限を超えたときに打ち切れない
2. **読み切れなかったときの保険になる。** 完全読みでも深さ 1 から順に反復するため、時間内に空きマス数の深さへ到達できなくても、途中の深さの結果を返せる。「完全読みに挑戦して失敗したら手が無い」という状態を作らない
3. 反復深化の再実行によるコストは、α-β では深さ `d` までの総ノード数が深さ `d` 単体とほぼ同じ桁に収まるため、実質的な損失は小さい

`think.ts` は完全読みに入る局面でも、`endgame.ts` が返す設定を `deepen` に渡すだけでよい。

## 7. 時刻の注入とテスト方法

### 7.1 注入する理由

`deps.now` を引数で受け取ることで、次の 2 つを同時に満たす。

- `@othello/cpu` は `node:*` を import できない（`../モジュール定義.md` §3.5 の eslint 制限）。`Date.now()` はグローバルなので制限には触れないが、直接呼ぶとテストが実時間に縛られる
- **上限遵守のテストを実時間 0ms で書ける**

### 7.2 擬似時計を用いたテスト

呼ばれるたびに一定量進む時計を注入する。

```ts
/** 呼ばれるたびに step ミリ秒進む擬似時計 */
function fakeClock(step: number): () => number {
    let t = 0;
    return () => (t += step);
}
```

これにより「反復を 2 回終えた時点で上限に達し、3 回目を始めない」といった挙動を、実際に待たずに検証できる。`now` の呼び出し回数が挙動に影響するため、擬似時計を使うテストでは**呼び出し箇所を固定する**（§3.1 の擬似コードで `deps.now()` を呼ぶのは、反復開始前の判定・反復開始時刻・反復終了時刻・全体の開始と終了に限る）。

より細かい制御が要る場合は、時刻の配列を順に返す時計を用いる。

```ts
function scriptedClock(values: readonly number[]): () => number {
    let i = 0;
    return () => values[Math.min(i++, values.length - 1)]!;
}
```

## 8. テスト観点

要件定義 §17 の「思考時間上限を守ること」に対応する。

| #   | 観点                       | 内容                                                                          |
| --- | -------------------------- | ----------------------------------------------------------------------------- |
| 1   | 到達深さの決定性           | 擬似時計を固定すれば、同じ局面・同じ設定で到達深さと返す手が常に同じになる    |
| 2   | 上限遵守（基本）           | 上限に達した時点で次の反復を始めない。`depth` が想定どおりで止まる            |
| 3   | 上限遵守（予測判断）       | 直前の反復が長かった場合、まだ上限に余裕があっても次を始めない（§3.3）        |
| 4   | `maxDepth` での打ち切り    | 時間が余っていても `maxDepth` を超えて探索しない                              |
| 5   | 終局到達での打ち切り       | `exhausted` が立った反復で即座に抜け、以降の深さを試さない                    |
| 6   | 最悪ケースのフォールバック | 上限を 0 に近づけても `moves` が空にならず、`depth: 0` で合法手を返す（§4.2） |
| 7   | 打ち切り時の手の妥当性     | 途中で打ち切っても、返る手が必ず `listLegalMoves` に含まれる合法手であること  |
| 8   | 同点手の列挙               | 評価が並ぶ局面で `moves` が複数返ること（`think.ts` の乱択が機能する前提）    |
| 9   | 事前条件違反               | 合法手が無い局面で呼ぶと例外になること                                        |
| 10  | 盤面の不変                 | 呼び出しの前後で引数の盤面が変化しないこと                                    |

観点 1〜6 は擬似時計により実時間を待たずに検証する。観点 7・8 は `search.ts` のテストと重なるが、打ち切りが起きた状態での検証としてここにも置く。
