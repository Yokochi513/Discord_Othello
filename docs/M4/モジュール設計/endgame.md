## 1. 位置づけと関連要件

`endgame.ts` は **終盤の完全読み**を担う。ただし探索そのものを実行するモジュールではなく、「いま完全読みに入るべきか」の判定と、「完全読みとはどういう探索設定か」の定義を提供する。

| 要件          | 内容                                                                                        | 本モジュールでの扱い                                    |
| ------------- | ------------------------------------------------------------------------------------------- | ------------------------------------------------------- |
| 要件定義 §9.1 | 「つよい」: 探索深さ 8 以上、位置評価・着手可能数・確定石を含む評価関数、**終盤は完全読み** | 「終盤は完全読み」の部分が本モジュールの責務            |
| 要件定義 §9.2 | 思考時間に上限を設ける                                                                      | 上限の管理は行わない。`deepening.ts` に委ねる（§4）     |
| 要件定義 E-12 | 思考が上限時間を超えた → その時点の最善手を打つ                                             | 同上。完全読みを独立実行しないことで担保を 1 か所に保つ |
| 要件定義 §6   | 勝敗は終局時の石数が多い方の勝ち。同数は引き分け                                            | 完全読みの目的関数の選定根拠（§6）                      |
| 要件定義 O-06 | 探索深さ・思考時間上限は実測で決定する（期限 M4）                                           | 完全読みへ切り替える閾値も O-06 の対象に加える（§7）    |

「やさしい」「ふつう」は完全読みを行わない。`LevelConfig` に `endgameThreshold` を持つのは `algorithm: "search"` の強度のみで、そのうち「ふつう」は閾値 0（＝完全読みに入らない）を指定できる。

## 2. 完全読みとは何か

**完全読みは `search.ts` と別のアルゴリズムではない。** 残りの空きマス数を探索深さとし、評価関数を使わずに終局まで読み切る α-β 探索である。

| 項目       | 中盤の探索                                    | 完全読み                                         |
| ---------- | --------------------------------------------- | ------------------------------------------------ |
| 探索器     | `search.ts` の α-β                            | 同じ `search.ts` の α-β                          |
| 深さ       | `maxDepth`（強度ごとに固定）                  | 残りの空きマス数                                 |
| 末端の評価 | `evaluate.ts`（位置・着手可能数・確定石など） | 石差のみ（`evaluate.ts` を石差の重みだけで使う） |
| 得られる値 | 局面の良し悪しの推定                          | **その局面からの最終石差**（推定ではなく確定値） |
| 着手順序   | 評価値による並べ替え                          | 終盤向けの並べ替え（§5）                         |

深さを空きマス数と等しく取れば、探索木のすべての葉が終局に到達する。したがって末端で評価関数を呼ぶ必要はなく、`core` の `countCells` から得た石差がそのまま確定値になる。

### 2.1 パスは深さを消費しない

「深さ＝空きマス数」で必ず終局に到達するためには、**パスが深さを消費してはならない**。パスでは盤面の石が増えないため、パスを 1 手と数えると深さが足りなくなる。

これは `search.ts` 側の契約とする（`search.md` 参照）。`core` の `nextTurn` はパスを `{ kind: "pass" }` として返すため、探索側はこれを見て深さを据え置いたまま手番だけ入れ替える。両者パス（`{ kind: "bothPassed" }`）は終局であり、そこで打ち切る。

## 3. 公開 API

### 3.1 `isEndgame`

```ts
/**
 * 盤面が完全読みに入る段階かを判定する。
 * @param board 対象の盤面
 * @param threshold 完全読みに入る空きマス数の上限
 * @returns 空きマス数が threshold 以下なら true
 */
export function isEndgame(board: Board, threshold: number): boolean;
```

空きマス数は `@othello/core` の `countCells(board).empty` で数える。`CellCount` は `Readonly<Record<Cell, number>>` で `empty` を含むため、専用の数え上げは実装しない。

```ts
return countCells(board).empty <= threshold;
```

`threshold` が 0 以下なら常に `false` を返す（完全読みを無効にする指定として使える）。

### 3.2 `endgameConfig`

```ts
/**
 * 完全読み用の探索設定の差分を返す。
 * @param board 対象の盤面
 * @returns 強度の探索設定へ上書きする項目
 */
export function endgameConfig(board: Board): EndgameOverride;
```

```ts
/** 完全読みのために強度の設定へ上書きする項目 */
export type EndgameOverride = {
    /** 目標深さ。残りの空きマス数と等しい */
    readonly maxDepth: number;
    /** 末端評価の重み。石差のみを有効にし、他の成分は 0 にする */
    readonly weights: EvalWeights;
    /** 着手順序の方針（§5） */
    readonly ordering: "endgame";
};
```

**全体ではなく差分を返す。** `timeLimitMs` と `minThinkMs` は強度（`level.ts`）が持つ値をそのまま使うため、本モジュールは関与しない。`think.ts` が次のように合成する。

```ts
const config = configOf(level);
if (config.algorithm === "search" && isEndgame(board, config.endgameThreshold)) {
    const result = deepen(board, player, { ...config, ...endgameConfig(board) }, deps);
    // ...
}
```

## 4. 切替の判断者と実行経路

| 役割             | 担当           | 内容                                         |
| ---------------- | -------------- | -------------------------------------------- |
| 切替の**判断**   | `think.ts`     | `isEndgame` を呼び、完全読みに入るかを決める |
| 設定の**提供**   | `endgame.ts`   | `endgameConfig` で上書き項目を返す           |
| 探索の**実行**   | `deepening.ts` | 反復深化と時間管理。完全読みも必ずここを通る |
| 探索木の**走査** | `search.ts`    | 固定深さの α-β。中盤も完全読みも同じ実装     |

**`endgame.ts` が自分で探索を実行しない**のは、要件定義 E-12 の担保を 1 か所に保つためである（`../モジュール定義.md` §4「完全読みの経路」）。完全読みを別経路で走らせると時間上限の管理が 2 か所に分かれ、ラズパイで空きマス 12 の完全読みが上限を超えたときに打ち切れない。

`deepening.ts` を通すことには、上限の担保に加えて次の利点がある（`deepening.md` §6）。

- 深さ 1 から順に反復するため、**時間内に読み切れなくても途中の深さの結果が使える**。「完全読みに挑戦して失敗したら手が無い」という状態を作らない
- 全変化が終局に到達した反復では `exhausted` が立ち、それ以上深くせずに終わる。完全読みの自然な終了点になる

## 5. 終盤向けの着手順序

α-β 枝刈りは**良い手を先に調べるほど効く**。探索する手の順序は結果を変えないが、計算量を数倍から数十倍変える。中盤と終盤では良い並べ方が異なる。

| 段階 | 並べ方                                                                  | 理由                                                                                             |
| ---- | ----------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------ |
| 中盤 | `evaluate.ts` の評価値が高い順                                          | 評価関数が局面の良し悪しを推定できる。推定が当たるほど枝刈りが効く                               |
| 終盤 | 相手の着手可能数が少なくなる手を優先（mobility 順）。次いで隅・辺を優先 | 終盤では評価関数を使わないため、評価値で並べられない。相手の選択肢を狭める手は実際に良い手が多い |

終盤で評価値による並べ替えが使えないのは、**完全読みでは末端以外に評価値が存在しない**ためである。中盤の探索では深さ 1 の評価値を並べ替えに流用できるが、完全読みでは末端まで読んで初めて値が出る。そのため局面の形から直接決まる指標（着手可能数・隅の確保）を使う。

実装は「候補手ごとに 1 手だけ進めた盤面を作り、`listLegalMoves(next, opponent(player)).length` の昇順に並べる」で足りる。1 手分の `applyMove` と合法手列挙のコストはかかるが、枝刈りの改善がそれを上回る。

## 6. 勝敗のみを読むか、石差を最大化するか

完全読みの目的関数には 2 つの選択肢がある。

| 案                    | 内容                                  | 速度                                                           | 得られる手                           |
| --------------------- | ------------------------------------- | -------------------------------------------------------------- | ------------------------------------ |
| A. 勝敗のみ（WLD）    | 勝ち／負け／引き分けの 3 値だけを読む | **速い。** 値域が狭く α-β の窓がすぐ閉じるため枝刈りが強く効く | 勝てる手。ただし何目勝つかは問わない |
| B. 石差最大化（採用） | 最終石差を最大化する                  | 遅い。値域が -64〜+64 と広い                                   | 最終石差まで最善の手                 |

**採用は B（石差最大化）。** 理由は次のとおり。

1. **要件との整合。** 要件定義 §6 は勝敗を石数で定め、§7.4 の終局画面は最終石数を表示する。勝敗だけを最適化すると「勝ちが確定した後は投げやりな手を打つ」挙動になり、表示される石数が不自然になる
2. **`evaluate.ts` を再利用できる。** 石差は評価関数の一成分であり、重みを石差のみにすれば同じ `evaluate` で末端を評価できる。`../モジュール定義.md` §4 で決めた「評価関数は 1 本、成分の重みで切り替える」方針と一貫する。A を採ると完全読み専用の目的関数が別に必要になる
3. **家族が相手という利用シーン**（要件定義 §3）では、勝てばよいという打ち方より、終局まできちんと打つ挙動のほうが自然

速度が足りず閾値を十分に取れないと **O-06 の実測で判明した場合**は、A（WLD）へ切り替える、あるいは「まず WLD で読み、勝ちが確定したら石差で読み直す」二段構えを再検討する余地を残す。

## 7. 閾値と計算量

### 7.1 閾値は未確定値

完全読みに切り替える空きマス数の閾値（`LevelConfig.endgameThreshold`）は、**ラズパイでの実測により決定する**。

要件定義 §20 の O-06 は現在「CPU 各強度の探索深さと思考時間上限」しか挙げていないため、**本閾値を O-06 の対象に加える**必要がある（`../モジュール定義.md` §6）。

### 7.2 想定レンジと計算量の見積り

**想定は 10〜14。** 実測前の暫定値としては 10 を置き、`bench.ts` の結果で引き上げる。

α-β 探索が調べるノード数は、着手順序が理想的な場合でおよそ `b^(d/2)`（`b` は平均分岐数、`d` は深さ）になる。終盤は空きマスが減るにつれ分岐も減るため `b` は 8 前後と見込まれる。

| 空きマス数 | 見積りノード数（`b = 8`） | 備考                                                               |
| ---------- | ------------------------- | ------------------------------------------------------------------ |
| 10         | 8^5 ≒ 3.3 万              | 余裕がある                                                         |
| 12         | 8^6 ≒ 26 万               | 現実的な上限の目安                                                 |
| 14         | 8^7 ≒ 210 万              | 着手順序が悪いと一気に厳しくなる                                   |
| 16         | 8^8 ≒ 1,700 万            | 現構成（置換表を持たない。§7.3）では秒オーダーに収まらないと見込む |

**空きマスが 2 増えるごとに約 `b` 倍（8〜10 倍）**になる。閾値を 1 つ上げる判断は、直前の値の 3 倍程度の時間を許容することを意味する。

読み切れなかった場合でも `deepening.ts` の反復深化により浅い結果へ落ちるため（§4）、閾値を強気に置いても対局が壊れることはない。ただし浅い結果へ落ち続ければ「つよい」が名前倒れになる（要件定義 R-02）ため、実測に基づいて決める。

### 7.3 置換表を持たない判断

本実装では置換表（transposition table）を持たない。判断の根拠は `search.md` §6 と共通で、次の 3 点である。

| 観点       | 根拠                                                                                                                                   |
| ---------- | -------------------------------------------------------------------------------------------------------------------------------------- |
| 決定性     | 探索順序によって返す値・返す手が変わりうる。完全読みは**正解が一意に定まる**ためテストしやすい部分であり（§8）、この性質を崩したくない |
| メモリ制約 | worker は**対局中ずっと常駐**する（`../モジュール定義.md` §4）。表を持たせるとそのメモリを対局中ずっと占有する。要件定義 R-06          |
| 実装量     | Zobrist ハッシュ、エントリの置換戦略、世代管理が必要。要件定義 R-08                                                                    |

なお worker の常駐化により、**手をまたいで表を温める技術的な障害はなくなっている**。それでも見送るのは上記 3 点による判断である。

この判断は §7.2 の見積りに織り込み済みである。実測で閾値が想定を大きく下回る場合は、置換表の導入を最優先の改善候補として再検討する。終盤は同一局面への合流が中盤より多く、完全読みでの利得は特に大きい。

## 8. テスト観点

要件定義 §17 の「既知の局面で妥当な手を選ぶこと」に対応する。完全読みは**正解が一意に定まる**ため、CPU 思考の中で最もテストしやすい部分である。

| #   | 観点                        | 内容                                                                                                   |
| --- | --------------------------- | ------------------------------------------------------------------------------------------------------ |
| 1   | `isEndgame` の境界          | 空きマス数が `threshold` に等しいとき `true`、`threshold + 1` のとき `false`                           |
| 2   | `isEndgame` の無効指定      | `threshold` が 0 以下なら常に `false`                                                                  |
| 3   | `endgameConfig` の深さ      | `maxDepth` が `countCells(board).empty` と一致する                                                     |
| 4   | `endgameConfig` の重み      | 石差以外の成分の重みが 0 である                                                                        |
| 5   | 終盤の既知局面（残り 4〜6） | 手で数え上げた最善の決着と、完全読みが返す手が一致する                                                 |
| 6   | 結果と実際の終局の一致      | 完全読みが返した手を起点に最善応手で進め、`finishGame` の石差が読み筋の値と一致する                    |
| 7   | パスを含む終盤局面          | 片方が打てない局面を含むケースで、パスが深さを消費せず正しく終局まで読めること（§2.1）                 |
| 8   | 勝ち確定局面での石差最大化  | どの手でも勝てる局面で、最も石差の大きい手を選ぶこと（§6 の判断が効いていることの確認）                |
| 9   | 完封で終わる局面            | 一方の石が 0 枚になる変化を正しく終局と扱うこと（`core` の `detectGameEnd` が `shutout` を返すケース） |
| 10  | `deepening.ts` 経由での挙動 | 上限時間を極端に短くすると、完全読みに入っても浅い深さの結果が返ること（§4 の保険が働くことの確認）    |

観点 5・6 は、盤面を直接組み立てたテスト用局面を使う。`core` に `testHelpers.ts` があるため、盤面の構築はそこに揃える。
