## 1. 位置づけと関連要件

`cpuDriver.ts` は、**CPU の手番を検出して思考を走らせ、得られた着手を対局へ適用して配信するまで**を担う。`@othello/cpu` は盤面から着手を求める同期の純関数しか持たず、`gameSession.ts` は副作用のない状態遷移しか持たない。両者の間にある「いつ思考させるか」「どう非同期に待つか」「失敗したらどうするか」を引き受けるのがこのモジュールである。

| 区分     | 要件                                                                                                             |
| -------- | ---------------------------------------------------------------------------------------------------------------- |
| 機能要件 | F-04（CPU 着席）／F-06（盤面同期）／F-07（着手）／F-09（パス処理）／F-10（終局処理）／F-11（投了）／F-12（中断） |
| 仕様     | §9.2（思考はサーバー側・時間上限・思考中の表示・イベントループを塞がない）／§7.3（対局画面）                     |
| 非機能   | §12 CPU 思考時間（上限内に必ず着手する）／§12 リソース／§12 ログ                                                 |
| 異常系   | E-09（対局中の離脱＝無効試合）／E-12（思考が上限時間を超えた）／E-15（想定外の例外）                             |
| リスク   | R-02（性能不足で強度が名前倒れ）／R-03（イベントループ占有）／R-06（Sebastian と同居）                           |

### 1.1 責務の境界

| モジュール         | 持つもの                                                                          | 持たないもの                      |
| ------------------ | --------------------------------------------------------------------------------- | --------------------------------- |
| `@othello/cpu`     | 盤面から着手を求める同期の純関数（`think`）                                       | 状態・非同期・Node API・配信      |
| `cpuDriver.ts`     | worker の寿命管理、進行中思考の追跡、非同期の待ち合わせ、失敗時の判断、ループ制御 | 盤面ロジック・通知の組み立て      |
| `gameSession.ts`   | 副作用のない着手適用（`playSessionMove` 等）                                      | 非同期・CPU の存在                |
| `gameBroadcast.ts` | 着手後の配信の一本化                                                              | 誰が着手したか（人間／CPU）の区別 |

## 2. 駆動の契機

CPU の手番は次の 4 つの場面で発生する。呼び出し元を明示する。

| #   | 契機         | 呼び出し元                       | 条件                                                                            |
| --- | ------------ | -------------------------------- | ------------------------------------------------------------------------------- |
| 1   | 対局開始     | `webSocket.ts` `handleStartGame` | `start_game` を受理した直後、黒番が CPU であるとき（worker の起動もここで行う） |
| 2   | 再戦         | `webSocket.ts` `handleStartGame` | `rematch` で黒白が入れ替わった結果、黒番が CPU になったとき                     |
| 3   | 人間の着手後 | `webSocket.ts` `handleMove`      | 着手を受理し配信した後、手番が CPU 席へ移ったとき                               |
| 4   | 自動パス後   | **`cpuDriver.ts` 自身のループ**  | CPU の着手後に人間側が自動パスし、手番が CPU に戻ったとき                       |

契機 4 は WebSocket のハンドラからは呼ばれない。人間側に合法手が無いときの自動パスは `core` が着手適用の中で済ませるため（F-09）、**手番が CPU に戻った状態がそのまま返ってくる**。この再駆動はドライバ自身のループが担う（§3）。

なお、人間の着手の直後に **CPU 側が自動パスした場合**は手番が人間に戻るため、駆動は起きない。

**worker の寿命は「手番」ではなく「対局」に紐づく**（§6）。契機 1・2 では、駆動に先立って対局単位の worker を 1 つ起動する。契機 3・4 は既に生きている worker へ思考を依頼するだけで、起動は伴わない。黒番が人間の対局でも worker は対局開始時に起動しておく。人間が初手を考えている間に起動が済むため、**起動コストが最初の思考から隠れる**。

### 2.1 呼び出しの形

`driveCpuTurn` は待たない（fire-and-forget）。WebSocket のハンドラは人間への応答を返し終えており、CPU の思考完了を待つ理由が無い。ハンドラ側で `await` すると、その間そのソケットのメッセージ処理が止まる。

```ts
// handleMove の末尾（配信を済ませた後）
driveCpuTurn(turns, hub, connection.instanceId, deps);
return;
```

## 3. 状態遷移

```
                     driveCpuTurn(...)
                            │
                            ▼
                  ┌──────────────────┐
      ┌──────────►│ 手番判定          │
      │           │ ・対局がある      │
      │           │ ・未終局          │
      │           │ ・手番が CPU 席   │
      │           └────────┬─────────┘
      │            満たさない │ 満たす
      │            ┌────────┴─────────┐
      │            ▼                  ▼
      │      ┌──────────┐      ┌──────────────────┐
      │      │  待機     │      │  思考中           │
      │      │（何もせず │      │ greedy: 直接      │
      │      │  return） │      │ search: 常駐 worker│
      │      └──────────┘      │        へ依頼      │
      │                        └──────┬───────────┘
      │                                │
      │                    ┌───────────┴────────────┐
      │              成功  │                        │ 失敗・時間切れ
      │                    ▼                        ▼
      │            ┌──────────────┐        ┌──────────────────┐
      │            │ 最低思考時間  │        │ フォールバック    │
      │            │ の待ち合わせ  │        │（greedy を直接）  │
      │            └──────┬───────┘        └────────┬─────────┘
      │                   └───────────┬─────────────┘
      │                               ▼
      │                    ┌────────────────────┐
      │                    │ 適用前の再確認      │
      │                    │ ・同じ対局 ID       │
      │                    │ ・未終局            │
      │                    │ ・手番がまだ CPU    │
      │                    └────────┬───────────┘
      │                  一致しない  │ 一致する
      │                  （破棄）    ▼
      │                    ┌────────────────────┐
      │                    │ 着手適用 → 配信     │
      │                    │ gameBroadcast       │
      │                    └────────┬───────────┘
      │                             │
      └─────────────────────────────┘
          終局していなければ手番判定へ戻る
          （CPU が連続して着手しうる。F-09）
```

ループは次のいずれかで終わる。

- 手番が人間へ移った（待機へ。**worker は生かしたまま**次の手番を待つ）
- 対局が終局・投了・中断・離脱で終わった（**worker を破棄する**。§6・§12）
- 適用前の再確認に失敗した（結果を捨てて終了）

この図は 1 つの対局の中で繰り返し回る**手番単位**の遷移である。worker の起動と破棄はこの外側、**対局単位**で 1 回ずつ起きる（§6）。

**ループは必ず手番判定を経由する。** 「CPU が着手したのだから次も CPU」と決め打ちしない。盤面から手番を読み直すことで、連続パス・完封・盤面充填による終局（§6 の終局条件）をすべて `core` の判定に委ねられる。

## 4. 公開 API と型

```ts
/** 思考の実行経路。テストではこれを差し替えて worker を起動せずに検証する */
export type ThinkRunner = (request: ThinkRequest) => Promise<ThinkOutcome>;

/** worker（または in-process）へ渡す思考の依頼 */
export type ThinkRequest = {
    readonly gameId: string;
    readonly board: Board;
    readonly player: Player;
    readonly level: CpuLevel;
};

/** 思考の結果。fallback が true なら worker が使えずに貪欲手へ退避したことを示す */
export type ThinkOutcome = {
    readonly square: Square;
    readonly fallback: boolean;
    /** 到達した探索深さ。貪欲法では null（O-06 の調整材料としてログへ残す） */
    readonly depth: number | null;
    readonly elapsedMs: number;
};

/** 差し替え可能な依存。時刻・乱数・待機・ログを外から与える */
export type CpuDriverDeps = {
    readonly run: ThinkRunner;
    readonly now: () => number;
    readonly delay: (ms: number) => Promise<void>;
    readonly log: Pick<Console, "log" | "error">;
};

/**
 * CPU の手番であれば思考を走らせ、着手の適用と配信までを行う。
 * 手番が人間に移るか対局が終わるまで繰り返す（F-09 の自動パスにより CPU は連続着手しうる）。
 * 待たずに呼べる。呼び出し側は完了を待つ必要がない。
 */
export function driveCpuTurn(
    turns: CpuTurnStore,
    hub: WebSocketHub,
    instanceId: string,
    deps: CpuDriverDeps,
): void;

/**
 * 対局に紐づく worker を起動する。対局開始・再戦で呼ぶ。
 * 起動に失敗しても例外は投げず、ログへ記録して null のまま保持する（§9.4）。
 */
export function startCpuGame(
    turns: CpuTurnStore,
    instanceId: string,
    gameId: string,
    level: CpuLevel,
    deps: CpuDriverDeps,
): void;

/**
 * 進行中の思考を打ち切り、対局に紐づく worker を破棄する。
 * 終局・投了・中断・離脱・自動破棄で呼ぶ（§12.1 の 6 契機）。
 * 打ち切りが結果の返却と交差しても、適用前の再確認（§12.2）が誤適用を防ぐ。
 */
export function cancelCpuTurn(turns: CpuTurnStore, instanceId: string, gameId: string): void;

/** すべての worker を破棄する。サーバー停止時に呼ぶ（§12.1） */
export function disposeAllCpuWorkers(turns: CpuTurnStore): void;

/** 「対局 ID → worker と進行中の思考」を保持する。WebSocketHub が 1 つ持つ */
export class CpuTurnStore {
    /* §11 */
}
```

> **注記（モジュール定義書との差分）**
> `../モジュール定義.md` §3.3 では `cancelCpuTurn(instanceId, gameId)` と記していたが、本設計では第 1 引数に `CpuTurnStore` を取る。理由は、進行中思考の対応表をモジュールレベルの可変状態に置くと**テスト間で状態が漏れる**ためで、既存の `GameStore` / `LobbyStore` が「状態はインスタンスが持ち、ロジックは関数」で揃えているのと同じ形にする。一覧側の表記もこれに合わせて更新されたい。
> また worker を対局単位で常駐させる方針（D-03a の B への転換）に伴い、`startCpuGame` と `disposeAllCpuWorkers` の 2 つを公開 API に追加している。

## 5. 実行経路の振り分け

`@othello/cpu` の `level.ts` が返す `LevelConfig.algorithm` で分岐する。**強度名（`"easy"` 等）をハードコードしない。**

| `algorithm` | 経路            | 理由                                                                                                                                                          |
| ----------- | --------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `"greedy"`  | **in-process**  | 合法手の列挙と最大反転の比較だけで 1ms 未満。R-03 のイベントループ占有に当たらない。**この強度の対局では worker を一切起動しない**ため、V8 ヒープも消費しない |
| `"search"`  | **常駐 worker** | 反復深化する α-β 探索は秒オーダー。§9.2 が求めるとおり別スレッドで実行する。worker は対局単位で生かす（§6）                                                   |

in-process 経路は、§9 のフォールバックが使う経路と**同一のものを再利用する**。分岐は増えるが実装の増分は小さい。

```ts
const config = configOf(level);
const outcome =
    config.algorithm === "greedy"
        ? runInProcess(request, config, deps) // think() を直接呼ぶ
        : await runInWorker(request, config, deps);
```

## 6. worker のライフサイクル

**対局開始時に 1 つ起動し、対局が終わるまで生かす。** 思考ごとの起動・破棄はしない。

```
 対局開始（algorithm = "search" の CPU が着席している対局のみ）
   │
   ├─ new Worker(workerUrl)        ← §7 のパス解決。1 対局につき 1 回だけ
   │
   │   ┌──────────── 対局が続くあいだ繰り返す ────────────┐
   │   │                                                  │
   ├───┤ 親 → worker: postMessage({ requestId, board, player, level })
   │   │ worker    : think(board, player, level, deps) を同期実行
   │   │ worker → 親: postMessage({ requestId, square, depth, elapsedMs })
   │   │                                                  │
   │   └──────────────────────────────────────────────────┘
   │
   └─ 対局終了（§12.1 の 6 契機）→ worker.terminate()（確実に破棄）
```

### 6.1 なぜ常駐させるか（D-03a の転換）

当初は「思考ごとに起動・破棄」とし、後始末の単純さとメモリの軽さを理由に挙げていた。疎通確認で得た実測値を踏まえ、**対局単位の常駐へ方針を転換した**。

| 根拠                 | 内容                                                                                                                            |
| -------------------- | ------------------------------------------------------------------------------------------------------------------------------- |
| 起動コストが毎手載る | 実測（開発機）で `.ts` 約 107ms / `.js` 約 75ms。**ラズパイではさらに悪化する見込み**。1 局 60 手なら合計で無視できない量になる |
| 往復は 3 桁小さい    | 起動済み worker との 1 往復は **0.2〜0.3ms**。常駐させれば着手ごとの通信遅延は事実上消える                                      |
| 将来の余地           | 置換表（transposition table）を手をまたいで温める最適化が可能になる。M4 では見送るが（`search.md` §6）、道は残る                |

**代償は後始末の責務が増えることである。** 対局の終わり方すべてで worker を確実に破棄しなければならない（§12.1）。またメモリの占有が思考中だけでなくなる（§11.3）。

### 6.2 worker が失われた場合の再生成

`terminate()`・クラッシュ・`exit` イベントにより、対局の途中で worker が失われることがある。

1. worker が失われたら、保持している参照を `null` にする（この時点では何もしない）
2. 次に思考が必要になったとき、**1 回だけ再生成を試みる**
3. 再生成に成功すればそのまま思考を依頼する
4. **再生成に失敗した場合、その対局は以後 `greedy` のフォールバックに固定する**（`fallbackLocked`）。同じ対局で再生成を繰り返し試みることはしない

固定する理由は、起動に失敗する状況（`dist/cpuWorker.js` が無い、メモリ不足など）は 1 手のあいだに解消しないのが通例であり、毎手起動を試みても遅延とログを増やすだけだからである。固定した場合も §9.3 の記録と通知は行う。

### 6.3 worker へ渡す値

worker は常駐するため、値は **`workerData`（起動時に 1 回）ではなく `postMessage`（思考ごと）**で渡す。

| 値          | 用途                                                           |
| ----------- | -------------------------------------------------------------- |
| `requestId` | 依頼と結果の対応付け。古い依頼の結果を取り違えないための識別子 |
| `gameId`    | 結果に添えて返し、適用前の再確認に使う                         |
| `board`     | 探索の起点となる盤面                                           |
| `player`    | 思考する側の色                                                 |
| `level`     | 強度。worker 側で `configOf` を引き直す                        |

`timeLimitMs` は `level` から worker 側で導けるため渡さない。パラメータの正は `level.ts` の 1 か所に保つ（O-06 の調整をそこへ閉じるため）。

`requestId` は常駐化に伴って必要になった。使い捨てなら「その worker が返す結果は 1 つだけ」で済んでいたが、常駐 worker は複数の依頼を順に処理するため、**打ち切り後に届いた古い結果**を新しい依頼の結果と取り違えないための照合が要る。番号が一致しない結果は黙って捨てる。

### 6.4 盤面の凍結について

`core` の盤面は `Object.freeze` されているが、**構造化複製（structured clone）で worker へ渡ると凍結は保持されず、複製先は凍結されていない配列になる**。

worker 側で再凍結は**行わない**。理由は次の 2 点。

1. 探索・評価は盤面を破壊しない純関数であり、書き換える経路が存在しない
2. 思考ごとに新しい複製が届き、**worker 内でその盤面を保持し続ける主体がいない**。前の手の盤面は次の依頼が来た時点で参照されなくなる

2 点目は worker を常駐させても変わらない。常駐するのは**スレッドであって局面ではない**ためである。

`core` には `restoreGameState` という再凍結用の関数があるが、ここでは用いない。

## 7. worker エントリのパス解決

`new Worker(path)` に渡すのは **import 指定子ではなく実行時のパス文字列**である。`server/tsconfig.json` の `rewriteRelativeImportExtensions` は import 文の `.ts` を `.js` へ書き換えるが、**文字列リテラルやランタイムの URL 計算はその対象外**なので、自前で解決する必要がある。

3 つの実行環境で動かなければならない。

| 環境   | 起動                                                   | 実体                |
| ------ | ------------------------------------------------------ | ------------------- |
| 開発   | `node --experimental-strip-types --watch src/index.ts` | `src/cpuWorker.ts`  |
| 本番   | `node dist/index.js`（systemd）                        | `dist/cpuWorker.js` |
| テスト | vitest                                                 | `src/cpuWorker.ts`  |

### 7.1 解決の方法

`import.meta.url` を基準に**同じディレクトリの兄弟ファイル**を指し、拡張子は**自分自身の拡張子**から決める。

```ts
// cpuDriver.ts が .ts で動いていれば cpuWorker.ts、.js なら cpuWorker.js を指す
const extension = import.meta.url.endsWith(".ts") ? ".ts" : ".js";
const workerUrl = new URL(`./cpuWorker${extension}`, import.meta.url);
```

この方法の利点。

- 環境変数を増やさない（`/etc/othello/othello.env` とデプロイ手順 §16.3 に手が入らない）
- `process.cwd()` に依存しない。systemd の `WorkingDirectory` やテストの実行ディレクトリで壊れない

### 7.2 残るリスク

`--experimental-strip-types` 環境で `.ts` の worker が起動するかは、Node のバージョンと `execArgv` の継承挙動に依存する（`worker_threads` の `Worker` は既定で親の `execArgv` を継承する）。**この点は疎通確認で検証済みである**（`../モジュール定義.md` §7.1）。`.ts` worker は起動し、`execArgv` は既定で継承され、vitest からも追加設定なしで起動できる。ただし `fileURLToPath` を使わず `new URL(...).pathname` を直接渡すと Windows で壊れるため、上記の書き方を守ること。

## 8. ウォッチドッグ

§9.2 と E-12 は「**上限内に必ず着手する**」ことを求める。上限そのものは `deepening.ts` が反復深化の中で守るが、それは**探索が正常に動いている前提**の話である。worker の起動失敗・無応答・例外では `deepening.ts` に制御が渡らない。ドライバ側の番人が要る。

```
 思考の依頼
   │
   ├─ タイマー開始: deadline = now() + timeLimitMs + graceMs
   │
   ├─ 期限内に結果 → タイマー解除、結果を採用（worker はそのまま生かす）
   │
   └─ 期限超過    → worker.terminate() → 参照を null に → フォールバック（§9）へ
                     ※ 次の思考で 1 回だけ再生成を試みる（§6.2）
```

**期限超過での `terminate()` は常駐 worker を殺す。** 使い捨てだった頃は「どのみち捨てる worker を早めに捨てる」だけだったが、常駐方式では対局の途中でスレッドが失われることを意味する。そのため §6.2 の再生成が必要になる。

### 8.1 猶予（`graceMs`）の考え方

`timeLimitMs` は**探索そのものの上限**であり、盤面の構造化複製と結果メッセージの往復（実測 0.2〜0.3ms）は含まれていない。猶予はこれを吸収する余白である。

常駐化により、**猶予が worker の起動時間を吸収する必要はほぼ無くなった**。起動は対局開始時に済んでおり（§2）、思考のたびに待つのは往復だけである。例外は §6.2 の再生成が走る手で、このときだけ起動時間（実測 75〜107ms、ラズパイではさらに悪化）が上乗せされる。

**初期値は 1000ms** とし、O-06 の実測（`bench.ts` と実機での対局）に合わせて調整する。再生成が走る手を吸収できる程度の余白を残す。猶予が短すぎると正常な思考を殺し、長すぎると無応答の検知が遅れて画面が「思考中」のまま留まる時間が伸びる。

猶予の値は `level.ts` ではなくドライバ側の定数とする。強度ごとに変える理由が無く、実行基盤の性質にのみ依存するため。

## 9. フォールバック

### 9.1 発動条件

| 事象                    | 具体例                                                          |
| ----------------------- | --------------------------------------------------------------- |
| worker の起動失敗       | 本番で `dist/cpuWorker.js` が存在しない、パス解決の誤り         |
| **worker の再生成失敗** | §6.2 の再生成にも失敗した（以後その対局は固定でフォールバック） |
| worker 内の例外         | 探索の実装不具合、メモリ不足                                    |
| **worker の異常終了**   | 対局中に `exit` / `error` が発生した（その手はフォールバック）  |
| 無応答                  | §8 のウォッチドッグが期限超過を検知                             |

### 9.2 扱い

**`greedy` を in-process で実行し、その手を打って対局を続行する。**

E-15 は「想定外の例外はログへ記録し、**対局は破棄せず現在の局面を保持**する。利用者には汎用のエラー表示を出す」と定めている。これに従い、対局を終わらせない。

手番を CPU のまま放置する選択は取らない。D-08 の決定により画面の「思考中」は**手番が CPU 席であることから導出**されるため、放置すると §9.2 の「対局が固まったように見えないようにする」に正面から反する。復帰手段が中断（＝無効試合、戦績に残らない）しか無くなるのも損である。

### 9.3 記録と通知（必須）

フォールバックの発動は、**必ず**次の 2 つを行う。

1. `log.error` へ記録する（§12 ログ: エラー）。対局 ID・強度・原因（起動失敗／例外／無応答）を残す
2. ルームへ `error` メッセージを 1 回配信する（E-15 の「汎用のエラー表示」）

> **R-02 の別経路への警戒**
> 本番で worker が**恒常的に**失敗していると、「つよい」を選んだのに実際には毎手「やさしい」相当の貪欲手が打たれる。盤面は進み、対局も終局まで到達するため、**何も壊れていないように見えたまま強度だけが名前倒れになる**。R-02 は「ラズパイの性能が探索に耐えない」リスクとして挙げられているが、これはその別経路である。ログと通知を省略してはならない。
>
> §6.2 の「再生成に失敗したらその対局は固定でフォールバック」は、この危険を**対局単位で確定させる**挙動である。固定した時点で 1 回だけ通知が出るため、利用者はその対局が貪欲手で進むことを知ることができる。

### 9.4 起動失敗をその場でエラーにしない理由

`startCpuGame`（§4）は対局開始時に worker の起動を試みるが、失敗しても例外を投げず、ログへ記録して参照を `null` のままにする。

対局開始の時点では**まだ思考が必要とは限らない**（黒番が人間なら最初の思考は数十秒後）。起動失敗を対局開始の失敗として扱うと、貪欲手でなら成立したはずの対局まで始められなくなる。E-15 の「対局は破棄せず現在の局面を保持する」方針とも整合しない。

実際に思考が必要になった時点で §6.2 の再生成が走り、そこで初めてフォールバックの判断が下る。

## 10. 最低思考時間

**「思考の完了」と「最低時間の経過」の両方を待ってから着手を適用する。**

```ts
const [outcome] = await Promise.all([deps.run(request), deps.delay(config.minThinkMs)]);
```

### 10.1 理由

D-19 により「やさしい」は in-process で 1ms 未満に着手を返す。クライアントは `state` メッセージの**スナップショット**で盤面を描き直すため、人間の着手と CPU の着手が 1ms 差で届くと、**人間は自分の手が盤に乗った瞬間を目にしないまま**、2 手進んだ盤面を見ることになる。

これは §7.3 の 2 つの要求と衝突する。

- 「石の反転は**アニメーションさせる**」— 人間の着手の反転アニメーションが、CPU の手による再描画で潰れる
- 「**直前に打たれた手**を盤面上で示す」— 人間が自分の手の位置を確認する前に、印が CPU の手へ移る

### 10.2 なぜサーバー側で待つか

クライアント側で状態スナップショットを待ち行列にして順に再生する案もあるが、採らない。再接続・途中参加では**サーバーが現在の状態だけを送る**設計であり（D-08 でこの性質を活かして「思考中」を導出している）、履歴を前提にした再生機構と衝突する。

サーバー側で待てば実装は `Promise.all` 1 か所で済み、待っている間は「思考中」表示が出るため、**空白ではなく CPU が考えている演出**として読める。

### 10.3 値

`level.ts` の `LevelConfig.minThinkMs` が持つ。「ふつう」「つよい」は探索が元々この値を超えるため実際に効くのは「やさしい」だけである。値は O-06 の調整対象に含める。

## 11. worker と進行中思考の追跡

### 11.1 なぜ状態を持つか

`@othello/cpu` の `think()` は状態を持たない同期の純関数である。一方ドライバは**「対局 ID → worker と進行中の思考」の対応表を保持する**。用途は 4 つ。

1. 対局単位で常駐する worker への参照を保つ（§6）
2. §8 のウォッチドッグが期限超過時に `terminate` する対象を特定する
3. 投了・中断・離脱（§12）で、まだ走っている思考を打ち切り、worker を破棄する
4. 再生成に失敗した対局を記憶し、以後のフォールバックを固定する（§6.2）

この役割分担は意図的なものである。思考そのものを純粋に保ったまま、**寿命の管理だけを Node 側へ寄せる**。常駐化によりこの「寿命の管理」の比重は増えたが、`@othello/cpu` 側は同期の純関数のままで変わらない。

### 11.2 保持する内容

```ts
type CpuGame = {
    readonly gameId: string;
    readonly level: CpuLevel;
    /** 対局単位で常駐する worker。未起動・喪失時は null（§6.2） */
    worker: Worker | null;
    /** 再生成に失敗し、以後この対局は貪欲手で進める（§6.2） */
    fallbackLocked: boolean;
    /** 進行中の思考。思考していなければ null */
    inflight: CpuTurn | null;
};

type CpuTurn = {
    /** 依頼と結果の照合に使う番号（§6.3） */
    readonly requestId: number;
    /** ウォッチドッグのタイマー */
    readonly watchdog: NodeJS.Timeout;
    /** 打ち切られたか。結果が返っても適用しない印 */
    cancelled: boolean;
};

class CpuTurnStore {
    readonly #games = new Map<string, CpuGame>(); // key: instanceId
    // start / get / delete / cancel / disposeAll
}
```

鍵は `instanceId` とする。要件定義 §12 の同時対局数は 3 で、**Activity インスタンスごとに対局は 1 局**（`GameStore` が同じ粒度で保持している）。同じインスタンスで思考が二重に走ることは、手番がひとつしか無い以上あり得ない。

`CpuGame` は対局の寿命、`CpuTurn` は 1 手の寿命を表す。常駐化により**寿命の異なる 2 層**が生じたため、型を分ける。

### 11.3 メモリ（R-06 の再評価）

**常駐化の代償が最も直接に現れるのがここである。** 使い捨て方式では V8 ヒープを余分に抱えるのは思考中だけだったが、常駐方式では**人間が手を考えているあいだも worker が生きたままヒープを保持する**。

| 項目                       | 内容                                                                                                        |
| -------------------------- | ----------------------------------------------------------------------------------------------------------- |
| 同時に生きる worker の上限 | **3**。§12 の同時 3 対局が上限で、D-16a により各対局で少なくとも 1 席は人間のため CPU 席は 1 局につき最大 1 |
| `greedy` 強度の対局        | worker を起動しないため 0（§5）                                                                             |
| 占有される期間             | 対局開始から終局・投了・中断・離脱まで。人間の手番中も含む                                                  |
| 解放                       | §12.1 の 6 契機すべてで `terminate()`。取りこぼすとリークする                                               |

要件定義 R-06（Sebastian と同居するメモリ不足）に対して、この構成は使い捨て方式より重い。**worker 3 つ分の常駐ヒープが Sebastian と共存できるかは `bench.ts` での実測対象に加える**（`../モジュール定義.md` §7.3）。実測で収まらない場合の退避先は、①`greedy` を除く同時対局数の制限、②使い捨て方式への差し戻し、の順に検討する。

## 12. 競合と後始末

### 12.1 打ち切りを呼ぶ場所

常駐方式では、**対局の終わり方すべてで worker を確実に破棄する**ことがドライバの責務になる。取りこぼすとスレッドとヒープがリークする（§11.3）。

| #   | 事象                 | 呼び出し元                                 | 対応要件 |
| --- | -------------------- | ------------------------------------------ | -------- |
| 1   | 終局                 | `gameBroadcast` の `broadcastGameEnd` の後 | F-10     |
| 2   | 投了                 | `webSocket.ts` `handleGameEnd`（`resign`） | F-11     |
| 3   | 中断                 | `webSocket.ts` `handleGameEnd`（`abort`）  | F-12     |
| 4   | 対局中の離脱         | `socket.on("close")` の `abandonGame` の後 | E-09     |
| 5   | 進行中対局の自動破棄 | 保持期間切れの掃除処理（**M5 で実装**）    | §11.4    |
| 6   | サーバー停止         | プロセス終了処理（`disposeAllCpuWorkers`） | §16      |

1〜5 は `cancelCpuTurn(turns, instanceId, gameId)` を呼ぶ。この関数は `cancelled` を立て、ウォッチドッグのタイマーを解除し、**`worker.terminate()` で常駐 worker を破棄**して、`CpuTurnStore` から対局のエントリを削除する。6 は `disposeAllCpuWorkers(turns)` で全インスタンス分をまとめて破棄する。

**1（終局）は使い捨て方式では不要だった契機である。** 使い捨てなら着手を返した時点で worker は既に無く、終局で後始末するものが残らなかった。常駐方式では、CPU の着手で終局した場合も worker が生きたままになるため、明示的な破棄が要る。

**5 は M5 の掃除処理に接続する。** M4 の時点では実装されないが、掃除処理を書く際に `cancelCpuTurn` の呼び出しを忘れると、破棄された対局の worker が残り続ける。M5 への申し送り事項として記録する。

### 12.2 打ち切りだけでは足りない

`terminate()` の要求と worker からの結果返却は**交差しうる**。`postMessage` が済んだ直後に `terminate()` を呼んでも、親側のメッセージハンドラは既にキューへ載った結果を受け取る。したがって打ち切りは競合防止の本体ではない。

常駐方式ではもう 1 つ交差の経路がある。**打ち切られた依頼の結果が、同じ worker への次の依頼の結果として届く**ように見えるケースである。これは §6.3 の `requestId` で照合し、番号の一致しない結果を捨てることで塞ぐ。以下の 3 条件はその後段の防壁である。

**本体は「適用前の再確認」である。** 思考結果を適用する直前に、次の 3 つをすべて確かめる。

```ts
// ① 対局が入れ替わっていないか（中断→再戦で新しい対局が始まっている場合を含む）
if (!hub.authorizesGame(instanceId, outcome.gameId)) return;

const session = hub.game(instanceId);
if (session === null) return;

// ② 既に終局・投了・中断・離脱で終わっていないか
if (isFinished(session)) return;

// ③ 手番がまだ CPU 席か
const turn = session.state.turn;
if (turn === null || session.players[turn].kind !== "cpu") return;
```

①は `WebSocketHub.authorizesGame`（内部では `GameStore.isCurrentGame`）をそのまま使える。**中断直後に再戦を始めた場合**、古い思考が返しても対局 ID が一致しないため捨てられる。

この 3 条件を通らなかった結果は**黙って捨てる**。エラー通知はしない。正常な打ち切りの帰結であり、利用者に見せる事象ではない。

### 12.3 適用に使う入口

`GameStore.play()` は `userId` を引数に取り、`seatOf` で着手者の色を決める。CPU には `userId` が無いため、**`userId` を持たない CPU 着手用の入口を `gameSession.ts` と `WebSocketHub` に追加する**（`../モジュール定義.md` §3.3 の改修項目）。本設計では次の名前を提案する。

| 層               | 追加する関数                                          |
| ---------------- | ----------------------------------------------------- |
| `gameSession.ts` | `playCpuMove(session, square): MoveResult`            |
| `GameStore`      | `playCpu(instanceId, gameId, square): MoveResult`     |
| `WebSocketHub`   | `playCpuMove(instanceId, gameId, square): MoveResult` |

`playCpuMove` は「手番の席が CPU であること」を検証したうえで `playMove`（core）へ委ねる。人間の着手と同じく、**非合法手はサーバー側で拒否される**（§5.4 / E-02）。CPU が非合法手を返した場合はドライバの不具合であり、E-15 として扱う（§13）。

### 12.4 再接続との関係

クライアントの再接続は思考に影響しない。思考はサーバー側で走り続け、完了時の配信は再接続後のソケットにも届く。再接続したクライアントは `state` のスナップショットから「手番が CPU ＝ 思考中」を導出する（D-08）。

サーバー再起動をまたぐ復元は M5 の範囲であり、本書では扱わない。

## 14. ログ出力

§12 は「対局の開始・終了・エラー・接続断を記録すること」を求める。既存の `webSocket.ts` が `対局開始:` `着手:` `対局終了:` などの日本語 1 行ログを出しているので、体裁を合わせる。

| 契機               | 例                                                                            | 水準    |
| ------------------ | ----------------------------------------------------------------------------- | ------- |
| CPU の着手         | `CPU着手: gameId=… level=strong square=e6 depth=8 elapsedMs=2140 path=worker` | `log`   |
| フォールバック発動 | `CPU思考に失敗: gameId=… level=strong cause=timeout 貪欲手で続行 square=d3`   | `error` |
| 打ち切り           | `CPU思考を打ち切り: gameId=… cause=abort`                                     | `log`   |
| 結果の破棄         | `CPU思考の結果を破棄: gameId=… cause=game_changed`                            | `log`   |

**`depth` と `elapsedMs` は必ず残す。** O-06（各強度の探索深さ・思考時間上限・完全読み閾値・最低思考時間）は実測で決める未決事項であり、`bench.ts` による合成条件での計測に加えて、**実際の対局で到達した深さと所要時間**が調整の一次資料になる。

ローテーションは journald に委ねる（§12）。

## 15. テスト観点

`CpuDriverDeps.run` を差し替えることで、**worker を起動せずに駆動ロジックだけを検証できる**。これが §4 で `ThinkRunner` を注入可能にした理由である。`now` / `delay` も注入されるため、最低思考時間やウォッチドッグの検証を実時間の待ちなしで書ける。

| #   | 観点                     | 確認内容                                                                                                             |
| --- | ------------------------ | -------------------------------------------------------------------------------------------------------------------- |
| 1   | 対局開始（黒が CPU）     | `start_game` 直後に思考が 1 回走り、着手が配信される                                                                 |
| 2   | 再戦で黒白が入れ替わる   | CPU が黒になった再戦で、開始直後に思考が走る                                                                         |
| 3   | 人間の着手後             | 手番が CPU へ移ったときだけ駆動される。CPU 側が自動パスして手番が人間に戻る場合は走らない                            |
| 4   | **連続手番**             | 人間に合法手が無く自動パスした局面で、CPU が続けて着手する（ループが回る）                                           |
| 5   | 終局で停止               | CPU の着手で終局したとき、ループが止まり `game_ended` が 1 回だけ配信される                                          |
| 6   | 経路の振り分け           | `algorithm` が `"greedy"` なら worker を起動しない                                                                   |
| 7   | 最低思考時間             | 思考が即座に終わっても `minThinkMs` 経過まで着手が適用されない（擬似時計で検証）                                     |
| 8   | ウォッチドッグ           | 期限を過ぎた思考が `terminate` され、貪欲手で続行する                                                                |
| 9   | フォールバックの記録     | 発動時に `log.error` と `error` 配信が**それぞれ 1 回**起きる                                                        |
| 10  | 打ち切り                 | 投了・中断・離脱で `cancelCpuTurn` が呼ばれ、後から返った結果が適用されない                                          |
| 11  | 対局の入れ替わり         | 中断→再戦の後に古い思考が返っても、対局 ID の不一致で捨てられる                                                      |
| 12  | 非合法手                 | `run` が非合法手を返した場合、拒否されて貪欲手で続行する                                                             |
| 13  | 空振り                   | 手番が人間・対局が無い・終局済みのいずれでも、何も起きずに return する                                               |
| 14  | **worker の使い回し**    | 同じ対局で 2 手続けて思考しても、worker の起動は 1 回だけである                                                      |
| 15  | **対局開始での起動**     | `algorithm` が `"search"` の CPU が着席した対局でのみ worker が起動し、`"greedy"` では起動しない                     |
| 16  | **6 契機での破棄**       | 終局・投了・中断・離脱・自動破棄・サーバー停止のそれぞれで `terminate` が呼ばれ、`CpuTurnStore` からエントリが消える |
| 17  | **再生成**               | 対局中に worker が死んだ後、次の思考で 1 回だけ再生成が試みられる                                                    |
| 18  | **フォールバックの固定** | 再生成に失敗した対局は以後 worker を起動せず、通知は 1 回だけ出る                                                    |
| 19  | **再戦で作り直す**       | 再戦では前の対局の worker が破棄され、新しい worker が起動する                                                       |
| 20  | **requestId の照合**     | 打ち切り後に古い番号の結果が届いても適用されない                                                                     |

`cpuWorker.ts` そのものの疎通（`.ts` / `.js` の両環境で起動するか）は**確認済み**である（§7.2）。

観点 14〜20 は常駐化に伴って追加したものである。`ThinkRunner` を差し替えるテストでは worker そのものが登場しないため、これらは **`CpuTurnStore` の状態遷移**（`worker` が `null` か否か、`fallbackLocked` が立つか、エントリが消えるか）を観測して検証する。worker の生成関数もまた注入可能にしておくと、起動失敗や異常終了を擬似的に起こせる。
