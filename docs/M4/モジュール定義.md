## 2. 全体構成

### 2.1 パッケージ構成（M4 完了時点）

```
packages/
  core/       盤面・合法手・反転・終局判定（Discord 非依存・テスト対象）
  cpu/        CPU 思考（探索・評価・反復深化）★M4 で新設
  protocol/   クライアント／サーバー間の通信の型（無依存）
  server/     HTTP / WebSocket / OAuth / REST API / 永続化 / CPU 思考の実行
  client/     React による画面
```

### 2.2 パッケージ依存

```
  protocol （依存なし）
      ▲
      ├──────────────┐
      │              │
   server ────────► cpu ────► core
      │                        ▲
      └── client ──────────────┘
```

- `cpu` は `core` にのみ依存する。`protocol` にも Node にも依存しない
- `protocol` は依存を持たない。`CpuLevel` は `protocol` と `cpu` が**それぞれ独立に定義**する（TypeScript の構造的型付けにより相互に代入可能。定義がずれればコンパイルエラーになる）
- `worker_threads` を用いた思考の実行は `server` の責務。`cpu` は同期の純関数のみを公開する

### 2.3 CPU 思考の実行経路

```
  対局開始 / 再戦 / 人間の着手 / 自動パス
        │
        ▼
  webSocket.ts ──► cpuDriver.ts ─┬─ algorithm = "greedy" ─► in-process で think()
                        │        └─ algorithm = "search" ─► cpuWorker.ts（対局単位で常駐）
                        │                                      └─ cpu の think() を同期実行
                        │
                        ├─ 対局開始で worker を起動し、対局の終わりまで保持
                        ├─ ウォッチドッグ（上限＋猶予で terminate）
                        ├─ 失敗時は greedy にフォールバック
                        ├─ 最低思考時間の待ち合わせ
                        └─ 適用前に 対局ID・未終局・手番 を再確認
                                 │
                                 ▼
                         gameBroadcast.ts（着手後の配信）
```

## 3. モジュール一覧

区分は **新規** / **改修** の 2 種。

### 3.1 `@othello/cpu`（新規パッケージ）

| モジュール     | 区分 | 責務                                                                                         | 主な公開 API                                           | 依存                                          | 対応要件         |
| -------------- | ---- | -------------------------------------------------------------------------------------------- | ------------------------------------------------------ | --------------------------------------------- | ---------------- |
| `index.ts`     | 新規 | パッケージの公開 API。re-export のみを行い実装を置かない（`core/index.ts` と同じ規約）       | —                                                      | 同パッケージ内                                | §5.3             |
| `level.ts`     | 新規 | 強度から探索パラメータを引く対応表。**O-06 の調整をこの 1 ファイルに閉じる**                 | `CpuLevel` / `LevelConfig` / `configOf`                | なし                                          | §9.1・O-06       |
| `think.ts`     | 新規 | 思考の入口。強度で貪欲法と探索を選び、終盤完全読みへの切替を判断し、最善手が複数なら乱択する | `think(board, player, level, deps)` / `ThinkDeps`      | `level` `greedy` `deepening` `endgame` `core` | §9.1・F-04       |
| `greedy.ts`    | 新規 | 「やさしい」。角が取れるなら取り、なければ最も多く返る手を選ぶ（探索なし）                   | `greedyMove(board, player)`                            | `core`                                        | §9.1             |
| `deepening.ts` | 新規 | 反復深化と思考時間管理。上限到達時点の最善手を返す。**完全読みも必ずここを通す**             | `deepen(board, player, config, deps)`                  | `search` `core`                               | §9.2・E-12・R-02 |
| `search.ts`    | 新規 | 固定深さの Minimax + α-β 枝刈り。時間に依存せず**決定的**                                    | `searchBestMoves(board, player, depth, evaluate)`      | `evaluate` `core`                             | §9.1             |
| `evaluate.ts`  | 新規 | 評価関数。石差・位置・着手可能数・確定石の各成分を**重みで合成**する                         | `evaluate(board, player, weights)` / `EvalWeights`     | `core`                                        | §9.1             |
| `endgame.ts`   | 新規 | 終盤完全読み用の探索設定（目標深さ＝空きマス数、評価は石差のみ）と終盤向けの着手順序         | `isEndgame(board, threshold)` / `endgameConfig(board)` | `core`                                        | §9.1             |
| `bench.ts`     | 新規 | O-06 実測用スクリプト。既知局面を各強度で思考させ、到達深さ・所要時間・選んだ手を出力する    | CLI（`node dist/bench.js`）                            | 同パッケージ全体                              | §17 実機・O-06   |

**`LevelConfig` の形**

```ts
type LevelConfig =
    | { algorithm: "greedy"; minThinkMs: number }
    | {
          algorithm: "search";
          maxDepth: number;
          timeLimitMs: number;
          minThinkMs: number;
          weights: EvalWeights;
          endgameThreshold: number;
      };
```

「やさしい」は評価関数を使わないため、強度パラメータは均質な表にならない。判別可能ユニオンで表す（`TurnResult`・`MoveEntry` と同じ流儀）。

**`ThinkDeps` の形**

```ts
type ThinkDeps = { now: () => number; random: () => number };
```

時刻と乱数を注入することで、探索・評価・反復深化のテストを環境非依存かつ決定的に行える。

**詳細設計で確定した補足**（`モジュール設計/` の各文書による）

- `deepen` は最善手を**配列で返す**。`searchBestMoves` が同評価の手をすべて返すことと、乱択が `think.ts` の責務であることとの整合による
- `endgameConfig(board)` は探索設定の全体ではなく**差分（オーバーライド）**を返す。`timeLimitMs` / `minThinkMs` を強度側に残し、`think.ts` が合成する
- **完全読みの目的関数は石差最大化**とする（勝敗のみを読む WLD より遅いが、終局石数が戦績に残るため）。実測で足りなければ WLD へ切り替える
- `search.ts` は**探索の途中で中断できない**（時刻を受け取らないため）。思考時間上限は「反復の境界でのソフト打ち切り」＋「`cpuDriver.ts` のウォッチドッグによるハード打ち切り」の二段構えで担保する。反復 1 回分の超過を許容し、直前の反復時間から次の反復を見送る予測判断で抑える。**この見積り係数も O-06 の実測対象**
- `core/index.ts` は `DIRECTIONS` / `step` / `isOnBoard` / `freezeBoard` と `Direction` 型を**再エクスポートしていない**（バレルの規約により内部専用）。確定石判定や着手順序で方向走査が必要なため、**`cpu` 側が方向ベクトルを自前で持つ**。`core` のバレルは広げない

### 3.2 `@othello/protocol`（改修）

| モジュール | 区分 | 責務                                           | 主な変更点                                                                                                                      | 依存 | 対応要件         |
| ---------- | ---- | ---------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------- | ---- | ---------------- |
| `index.ts` | 改修 | クライアント／サーバー間で交わす通信の型と検証 | `CpuLevel` / `Occupant` の追加、`Seat` と `GameState.players` の `Occupant` 化、`cpu_seat` / `cpu_leave` の追加、検証関数の拡張 | なし | F-04・§7.2・§1.3 |

**型の変更**

```ts
/** 座席に着く主体。人間と CPU を判別可能ユニオンで表す */
type Occupant =
    { kind: "human"; userId: string; displayName: string } | { kind: "cpu"; level: CpuLevel };

type CpuLevel = "easy" | "normal" | "strong";

type Seat = Occupant | null;
```

**メッセージの追加**

```ts
| { type: "cpu_seat"; seat: "black" | "white"; level: CpuLevel }
| { type: "cpu_leave"; seat: "black" | "white" }
```

- 既存 7 種が保つ「1 操作 1 メッセージ」の粒度に揃える
- `isClientMessage` は `seat` の妥当性と `level` の妥当性を検査する。`userId` / `instanceId` を含むメッセージを拒否する既存のなりすまし防止は変更しない
- 日本語ラベル（やさしい／ふつう／つよい）は `protocol` に持たせず、client の表示層で解決する

| `gameSession.ts`   | 改修 | 対局セッション。`players` を `Occupant` 化し、`userId` を持たない CPU の着手を受け付ける入口を設ける                                                                                          | CPU 着手用の関数を追加。純粋関数である方針は維持                                                                                        | `core` `protocol`                   | F-05・F-07                  |
| `webSocket.ts`     | 改修 | 接続と配信。`cpu_seat` / `cpu_leave` の分岐、着手後の配信処理を `gameBroadcast.ts` へ移設、CPU 駆動の呼び出し、対局終了時の思考の打ち切り                                                     | `WebSocketHub` に CPU 着手の入口を追加                                                                                                  | `gameBroadcast` `cpuDriver` 他      | F-04・F-06・E-09            |

**`cpuDriver.ts` が保持する状態**

`@othello/cpu` の `think()` は状態を持たない同期の純関数だが、`cpuDriver.ts` は「**対局 ID → worker と進行中の思考**」の対応表（`CpuTurnStore`）を保持する。worker を対局単位で常駐させるため、および ウォッチドッグでの `terminate` と投了・中断・離脱時の打ち切りに必要なため。状態は**モジュールレベルの可変変数ではなくインスタンス**として持ち、既存の `GameStore` / `LobbyStore` と同じ「状態はインスタンス、ロジックは関数」に揃える（テスト間で状態が漏れないため）。

**worker のライフサイクル**

| 契機                                                                     | 動作                                                                                                                                                         |
| ------------------------------------------------------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| 対局開始・再戦                                                           | `algorithm: "search"` の CPU が着席していれば worker を 1 つ起動する（`startCpuGame`）。**黒番が人間でも対局開始時に起動し、起動コストを初手の思考から隠す** |
| 思考                                                                     | 常駐 worker へ局面を送り、結果を受け取る（1 往復 0.2〜0.3ms）。要求と応答は `requestId` で照合し、打ち切った思考の遅れた応答を破棄する                       |
| 終局・投了・中断・離脱（E-09）・進行中対局の自動破棄（M5）・サーバー終了 | worker を破棄する。**6 経路すべてで確実に**                                                                                                                  |
| ウォッチドッグ発動・worker の異常終了                                    | その worker は失われる。次の思考で 1 回だけ再生成を試み、失敗すればその対局は以後 greedy 固定                                                                |

再戦は新しい対局なので、強度が同じでも worker を作り直す（対局単位という原則を単純に保つ）。

**CPU 駆動を呼ぶ契機**

| #   | 契機         | 呼び出し元                                                                       |
| --- | ------------ | -------------------------------------------------------------------------------- |
| 1   | 対局開始     | `webSocket.ts` の `handleStartGame`（CPU が黒番の場合）                          |
| 2   | 再戦         | `webSocket.ts` の `handleStartGame`（黒白入れ替えの結果 CPU が黒番になった場合） |
| 3   | 人間の着手後 | `webSocket.ts` の `handleMove`（手番が CPU に移った場合）                        |
| 4   | 自動パス後   | **`cpuDriver.ts` 自身のループ**                                                  |

人間側の自動パスは `core` が着手適用の中で済ませるため、4 は `webSocket.ts` からは呼ばれない。**`webSocket.ts` からの呼び出し点は 3 箇所**で、CPU が連続して着手するループはドライバ内部で閉じる。

**worker のパス解決**（疎通確認で実測済み。§7 参照）

`new Worker(path)` は import ではなく実行時のパス文字列であり、`rewriteRelativeImportExtensions` による拡張子の書き換え対象にならない。`import.meta.url` を基準に同じディレクトリの兄弟ファイルを指し、拡張子は**自分自身の拡張子**から決める（`.ts` で動いていれば `cpuWorker.ts`、`.js` なら `cpuWorker.js`）。

```ts
const self = fileURLToPath(import.meta.url); // Windows では必須
const workerPath = path.join(path.dirname(self), `cpuWorker${path.extname(self)}`);
const worker = new Worker(workerPath); // execArgv は明示しない（親から継承される）
```

- **`fileURLToPath`（または `import.meta.filename`）は必須**。`new URL(...).pathname` を直接使うと Windows で `C:\C:\...` となり壊れることを実測で確認した
- **`execArgv` は明示しない**。既定で親から継承され、`.ts` / `.js` の双方および vitest 配下で動く。明示すると vitest 由来の `--conditions` 等を落とすリスクだけが増える
- Node 22.23.2 では型ストリップが既定で有効なため `--experimental-strip-types` は不要だが、将来 Node が既定を変えた場合の保険として既存の `dev` / `probe` スクリプトの指定は残してよい

**`cpuWorker.ts` に課される制約**（いずれも実測で確認）

| 制約                                                                                                  | 帰結                                                                                                                                                   |
| ----------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------ |
| 型ストリップは **erasable syntax only**。`enum` / `namespace` / パラメータプロパティ / decorator 不可 | `cpuWorker.ts` とそこから読む全モジュールで使わない（`@othello/core` / `cpu` はビルド済み JS を読むため影響なし）                                      |
| worker 内の相対 import は **`.ts` 拡張子必須**                                                        | 既存の `allowImportingTsExtensions` + `rewriteRelativeImportExtensions` と整合するため、実質的な制約にならない                                         |
| vitest から起動した worker は **vite の変換を通らず素の Node がロード**する                           | worker のソースは vite の alias / モック / カバレッジに依存できない。**worker は薄い配線だけにし、ロジックは純関数として `.test.ts` から直接検証する** |
| `cpuWorker.ts` は**どこからも import されない**（実行時の文字列参照のみ）                             | `tsconfig.build.json` の `include: ["src"]` によってビルドされている。`include` を絞る変更をすると本番だけ壊れる                                       |
| `.ts` 直接実行時、worker は `@othello/cpu` の **`dist` を読む**（`exports` が `./dist/index.js`）     | 開発時も `cpu` パッケージのビルドが必要。`core` と同じ既存のワークフロー                                                                               |

**ロビーの挙動に関する注記**

CPU を座らせられるのは座席に着いている人のみとしたため、**両席 CPU は構造的に成立しない**。一方で「人間が着席 → CPU を座らせる → その人間が退席」により `黒=空席 / 白=CPU` が残りうる。この状態では誰も CPU を降ろせないが、誰かが空席に着けば降ろせるため行き詰まりにはならない。

## 4. 主要な設計判断と根拠

| 判断                        | 決定                                                                                                         | 根拠                                                                                                                                                         |
| --------------------------- | ------------------------------------------------------------------------------------------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| CPU 思考の置き場所          | 新パッケージ `@othello/cpu`                                                                                  | メモリ（R-06）の計測・調整時に `core` と切り離して扱える                                                                                                     |

## 7. 先行確認事項とリスク

### 7.1 `.ts` worker の疎通確認（**確認済み**）

M4 の最初期に潰すべき項目として挙げていた「`--experimental-strip-types` 環境で `.ts` の worker が起動するか」は、**開発機（Windows / Node 22.23.2）で実測により確認済み**。本節の結論を前提に実装してよい。

| 確認項目                                          | 結果                                                                                                                                        |
| ------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------- |
| `.ts` worker の起動                               | **可**。Node 22.23.2 は型ストリップが既定で有効（`process.features.typescript` が `strip`）でフラグ自体が不要                               |
| `execArgv` の継承                                 | **既定で親から子 worker へ継承される**。明示指定も有効                                                                                      |
| `import.meta.url` 基準の兄弟解決                  | **機能する**。ただし `fileURLToPath`（または `import.meta.filename`）が必須。`new URL(...).pathname` は Windows で `C:\C:\...` になり壊れる |
| vitest からの worker 起動                         | **可。追加設定なし**。既定 pool（`forks`）／`threads`／`vmThreads` のすべてで成功                                                           |
| 凍結済み 8×8 盤面の受け渡し                       | **可**。structured clone で凍結は解け、worker 側で破壊的に書き換えても親には波及しない（完全な別コピー）                                    |
| 起動コスト（開発機・中央値・各 15 回 × 3 セット） | `.ts` 約 **107ms** / `.js` 約 **75ms**（型ストリップのオーバーヘッドは約 +32ms）。worker 使い回し時の 1 往復は 0.2〜0.3ms                   |

### 7.2 起動コストの実測を受けた D-03a の変更

当初 D-03a は「思考ごとに worker を起動・破棄する（使い捨て）」と決めていたが、§7.1 の実測（起動 75〜107ms に対し 1 往復 0.2〜0.3ms）を受け、**対局単位で常駐する方式へ転換した**。

**転換の理由**

- 起動コストは毎手に載る。ラズパイでは開発機よりさらに悪化するため、60 手の対局では無視できない合計になる
- 常駐すれば起動は対局あたり 1 回で済み、着手ごとの遅延はほぼ消える（1 往復 0.2〜0.3ms）
- 将来 置換表を導入する余地が残る（§4 参照。M4 では見送る）

**常駐化によって増える責務**

| 事項                    | 内容                                                                                                                             |
| ----------------------- | -------------------------------------------------------------------------------------------------------------------------------- |
| 確実な破棄              | 終局・投了・中断・離脱（E-09）・進行中対局の自動破棄（M5）・サーバー終了の **6 経路すべて**で破棄する                            |
| worker の死亡からの復帰 | 次の思考で 1 回だけ再生成を試み、失敗すればその対局は以後 greedy 固定（§4）                                                      |
| アイドル中のメモリ占有  | 人間が考えている間も worker は生きている。同時に生きる worker は最大 3（§12 の同時 3 対局。D-16a により各対局で CPU 席は最大 1） |

**受け入れた代償**: メモリ（R-06）。使い捨てなら思考中しか占めなかった V8 ヒープを、対局中ずっと保持する。`bench.ts` での実測対象に加える。
